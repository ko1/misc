1. プロファイリングとは何か

1.1 プロファイリングの定義と目的

プロファイリングとは、プログラムの実行時の振る舞いを計測・分析する技術である。具体的には、CPU時間の消費、メモリの割り当てと解放、I/O待ち、ロック競合など、プログラムの実行に関わるさまざまなリソースの使用状況を測定する。

プロファイリングの主な目的は以下の通りである。

  • 性能ボトルネックの特定: どの関数・メソッドが最も多くの時間を消費しているかを特定する
  • リソース使用の最適化: メモリ使用量、CPU使用率などのリソース消費パターンを把握する
  • 回帰検出: バージョン間での性能劣化を検出する
  • キャパシティプランニング: 本番環境でのリソース必要量を見積もる

Important

プロファイリングとベンチマーキングは異なる。ベンチマーキングは「どれだけ速いか」を測り、プロファイリングは「なぜ遅いのか」を特定する。両者は補完的な関係にある。

1.2 プロファイリングの歴史

プロファイリングの歴史は、コンピュータサイエンスの歴史とともに歩んできた。

1.2.1 初期のプロファイリング（1970年代）

1979年、Unix V7にprofコマンドが登場した。これはプログラムカウンタ（PC）のサンプリングに基づく最初の実用的なプロファイラであった。コンパイラが-pオプションで関数の呼び出し回数カウントコードを挿入し、PCサンプリングと組み合わせることで関数ごとの実行時間を推定した。

1.2.2 gprofの登場（1982年）

gprofはSusan L. GrahamらによってUCバークレーで開発された。profの単純なPCサンプリングに加えて、コールグラフの情報を収集できるようになった。関数間の呼び出し関係と、各関数の実行時間を組み合わせることで、より有用なプロファイリングが可能になった。

// gprofの出力例（フラットプロファイル）
  %   cumulative   self              self     total

サンプリングプロファイラは、一定間隔でプログラムの状態（主にコールスタック）を記録する。統計的な手法であり、サンプル数が十分であれば、プログラムの振る舞いを高い精度で把握できる。

  • 短命な関数を見逃す可能性がある

2.2.2 計装方式

計装プロファイラは、関数の入口・出口にフックを挿入して、正確な実行回数と実行時間を計測する。

原理: コンパイラによる静的計装、またはランタイムによる動的計装により、各関数の開始と終了時にタイムスタンプと呼び出しカウンタを記録する。

    // 元のコード
    do_work();

    __profiler_exit("target_function");   // コンパイラが挿入
}

長所:

  • 正確な呼び出し回数を取得できる
  • すべての関数呼び出しを捕捉できる
  • コールグラフを正確に構築できる

短所:

  • オーバーヘッドが大きい（全関数に計装するとプログラムが数倍遅くなることもある）
  • 計装自体がキャッシュの振る舞いを変える
  • 本番環境での常時有効化は困難

3.1 ハードウェアパフォーマンスカウンタ（PMU）

現代のCPUには、Performance Monitoring Unit（PMU）と呼ばれるハードウェアユニットが内蔵されている。PMUはCPU内部のイベント（命令実行、キャッシュミス、分岐予測ミスなど）をハードウェアレベルでカウントする機能を提供する。

perf_eventsは、カーネルとユーザー空間の間で効率的にデータを転送するためにリングバッファを使用する。mmap(2)でユーザー空間にマッピングされ、コピーなしでデータを読み取れる。

// リングバッファのセットアップ
void *mmap_buf = mmap(NULL, (1 + 2^n) * page_size,
                      PROT_READ | PROT_WRITE, MAP_SHARED,
                      perf_fd, 0);

struct perf_event_mmap_page *header = mmap_buf;

// データの読み取り
while (header->data_tail != header->data_head) {
    struct perf_event_header *event =
        (void *)mmap_buf + page_size + (header->data_tail % data_size);

    // イベントを処理
    process_event(event);

    header->data_tail += event->size;
}

Note

リングバッファのサイズは2のべき乗ページ数でなければならない。小さすぎるとイベントが失われ（PERF_RECORD_LOST）、大きすぎるとメモリを浪費する。一般的には128〜512ページが適切である。

3.3 スタックウォーク技術

プロファイラがサンプルを取得する際、最も重要な情報はコールスタック（呼び出し履歴）である。現在の関数だけでなく、そこに至る呼び出し経路を知ることで、ボトルネックの原因を特定できる。

3.3.1 フレームポインタベース

最もシンプルなスタックウォーク方式。各関数がフレームポインタ（x86_64ではrbpレジスタ）を保存していることを前提に、フレームポインタチェーンをたどる。

│ ローカル変数      │

// フレームポインタベースのスタックウォーク
void walk_stack_fp(void **buffer, int max_depth) {
    void **fp = __builtin_frame_address(0);
    int depth = 0;

    while (fp && depth < max_depth) {
        void *return_addr = fp[1];  // リターンアドレス
        buffer[depth++] = return_addr;
        fp = (void **)fp[0];       // 前のフレームポインタ
    }
}

Warning

GCCやClangのデフォルト最適化（-O2以上）ではフレームポインタが省略される（-fomit-frame-pointer）。これにより、フレームポインタベースのスタックウォークが機能しなくなる。本番環境でプロファイリングする場合は、-fno-omit-frame-pointerでコンパイルすることを推奨する。

3.3.2 DWARFアンワインド

DWARFデバッグ情報に含まれるアンワインド情報（.eh_frameセクション）を使用してスタックを復元する方式。フレームポインタが省略されていても正確にスタックウォークできる。

DWARFアンワインド情報は、各命令アドレスに対して、現在のフレームのCFA（Canonical Frame Address）を計算するためのルールを提供する。

// .eh_frameの内容の概念表現
// アドレス範囲 → CFAの計算方法
0x4005a0..0x4005a8:  CFA = RSP + 8     // 関数プロローグ前
0x4005a8..0x4005b0:  CFA = RSP + 16    // push rbp後
0x4005b0..0x4005f0:  CFA = RBP + 16    // mov rbp, rsp後
0x4005f0..0x4005f8:  CFA = RSP + 8     // pop rbp後

DWARFアンワインドの問題点は処理コストが高いことである。カーネル内でDWARFを解釈するのは複雑であり、perfはユーザー空間でアンワインドを行うために--call-graph dwarfオプションでスタックメモリのコピーを記録する。

3.3.3 ORC（Oops Rewind Capability）

ORCはLinuxカーネル専用のアンワインド形式で、DWARFよりも単純で高速なアンワインドを実現する。2017年にJosh Poimboeufによって導入された。

ORCテーブルはDWARFの.eh_frameを簡略化したもので、各命令に対してスタックポインタのオフセットとフレームポインタの位置のみを記録する。

LBRはIntel CPUの機能で、最近の分岐命令の履歴（ソース→ターゲットのペア）を記録する。最新のCPUでは32エントリのリングバッファを持つ。

    uint64_t info;    // 予測ミスフラグなど
};
// LBRリングバッファ: 最新32個のCALL/RET命令を記録

LBRの利点は、カーネル内で高速にスタックウォークできることと、フレームポインタの有無に依存しないことである。perf record --call-graph lbrで利用できる。ただし、スタックの深さは32（LBRエントリ数）に制限される。

3.4 eBPF

eBPF（extended Berkeley Packet Filter）は、Linuxカーネル内で安全にプログラムを実行するための仕組みである。プロファイリングにおいては、カーネル内でデータの集約やフィルタリングを行うことで、カーネル-ユーザー空間間のデータ転送量を削減できる。

3.4.2 BPFプログラムの例：CPUプロファイラ

// BPFプログラム（概念コード）
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

// スタックトレースを格納するMap
struct {
    __uint(type, BPF_MAP_TYPE_STACK_TRACE);
    __uint(max_entries, 16384);
    __uint(key_size, sizeof(u32));
    __uint(value_size, 127 * sizeof(u64));  // 最大深度127
} stack_traces SEC(".maps");

// スタックトレースごとのカウントを格納するMap
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __uint(max_entries, 16384);
    __type(key, struct stack_key);
    __type(value, u64);
} counts SEC(".maps");

struct stack_key {
    u32 pid;
    int kernel_stack_id;
    int user_stack_id;
};

SEC("perf_event")
int do_perf_event(struct bpf_perf_event_data *ctx) {
    struct stack_key key = {};
    u64 *val, one = 1;

    key.pid = bpf_get_current_pid_tgid() >> 32;
    key.kernel_stack_id = bpf_get_stackid(ctx, &stack_traces, 0);
    key.user_stack_id = bpf_get_stackid(ctx, &stack_traces,
                                         BPF_F_USER_STACK);

    val = bpf_map_lookup_elem(&counts, &key);
    if (val)
        (*val)++;
    else
        bpf_map_update_elem(&counts, &key, &one, BPF_ANY);

    return 0;
}

Tip

eBPFベースのプロファイラは、カーネル内でスタックトレースを集約するため、大量のサンプルを取得してもユーザー空間へのデータ転送量が少ない。これにより、高頻度サンプリングでも低オーバーヘッドを実現できる。

3.5 USDT（User Statically Defined Tracing）

USDTは、アプリケーションやライブラリに埋め込まれた静的なトレースポイントである。DTraceのプローブ機構をLinuxに移植したもので、有効化されていない場合のオーバーヘッドはほぼゼロ（NOP命令）である。

// USDTプローブの定義（SystemTap形式）
#include <sys/sdt.h>

void gc_start(int generation) {
    DTRACE_PROBE1(mygc, gc__start, generation);
    // GC処理
}

void gc_end(int generation, size_t freed) {
    DTRACE_PROBE2(mygc, gc__end, generation, freed);
}

多くの言語処理系（CPython、Ruby、JVM、Node.js）がUSDTプローブを組み込んでおり、bpftraceやperf probeから利用できる。

# CPythonのUSDTプローブを利用した例
bpftrace -e 'usdt:/usr/bin/python3:python:function__entry {
    printf("%s %s:%d\n", str(arg0), str(arg1), arg2);
}'

3.6 Intel Processor Trace（PT）

Intel PTは、CPUが実行したすべての制御フロー（分岐の方向、ターゲット）を記録するハードウェア機能である。LBRと異なり、記録量に制限がなく、完全な実行トレースを取得できる。

Intel PTの出力パケット（簡略化）：
TNT: TNTTNTN    ← 条件分岐のTaken/Not-Taken
TIP: 0x4005f0   ← 間接分岐のターゲットアドレス
FUP: 0x400620   ← 割り込みや例外のアドレス
PSB:             ← 同期バリア（デコード開始点）

Intel PTのデータはメモリに書き出されるが、そのままでは人間が読める形ではない。バイナリのDisassemblyと組み合わせてデコードする必要がある。perfではperf record -e intel_pt//で記録し、perf scriptでデコードする。

Intel PTの主な用途は以下の通り。

  • 完全なコードカバレッジ計測: 実際に実行されたすべてのパスを記録
  • 高精度プロファイリング: サンプリングでは見逃す短命な関数も補足
  • デバッグ: クラッシュ直前の実行パスを再構成
  • セキュリティ: Control Flow Integrity（CFI）の検証

Caution

Intel PTのデータ量は非常に大きい（数百MB/秒に達することがある）。長時間のトレースにはストレージ容量に注意が必要である。通常はスナップショットモードまたはフィルタリングと組み合わせて使用する。

3.7 ARM Statistical Profiling Extension（SPE）

ARM SPEは、ARMv8.2-Aで導入されたハードウェアサンプリング機能である。Intel PEBSに相当する機能で、命令単位のサンプリングとメモリアクセスのレイテンシ計測が可能。

SPEの特徴は以下の通り。

  • CPUパイプライン内で統計的に命令をサンプリング
  • 各サンプルに対して、実行レイテンシ、キャッシュヒット/ミス情報、分岐予測結果を記録
  • サンプリングはハードウェアで自動実行され、割り込みによるスキッド（skid）の問題がない

Linuxではperf record -e arm_spe_0//で利用できる。クラウド環境（AWS Graviton3以降など）でのプロファイリングに特に重要性が増している。

サンプリングプロファイラは、統計的手法によりプログラムの実行プロファイルを取得する。定期的にプログラムの状態をサンプルし、十分な数のサンプルから実行時間の分布を推定する。

4.2 シグナルベースのサンプリング

Unix系OSで最も一般的なサンプリング方式は、タイマーシグナルを利用する方法である。

4.2.1 ITIMER_PROFとSIGPROF

setitimer(2)でプロセスCPU時間タイマー（ITIMER_PROF）を設定し、SIGPROFシグナルのハンドラでスタックトレースを取得する。

#include <signal.h>
#include <sys/time.h>
#include <execinfo.h>

#define MAX_STACK_DEPTH 128

// サンプルバッファ
struct sample {
    void *stack[MAX_STACK_DEPTH];
    int depth;
};

static struct sample samples[MAX_SAMPLES];
static volatile int sample_count = 0;

// SIGPROFハンドラ
void sigprof_handler(int sig, siginfo_t *info, void *ucontext) {
    if (sample_count >= MAX_SAMPLES) return;

    struct sample *s = &samples[sample_count];
    s->depth = backtrace(s->stack, MAX_STACK_DEPTH);
    sample_count++;  // アトミック操作が必要な場合がある
}

void start_profiling(int interval_usec) {
    // シグナルハンドラの設定
    struct sigaction sa = {
        .sa_sigaction = sigprof_handler,
        .sa_flags = SA_SIGINFO | SA_RESTART,
    };
    sigemptyset(&sa.sa_mask);
    sigaction(SIGPROF, &sa, NULL);

    // タイマーの設定
    struct itimerval timer = {
        .it_interval = { 0, interval_usec },
        .it_value = { 0, interval_usec },
    };
    setitimer(ITIMER_PROF, &timer, NULL);
}

Warning

SIGPROFはプロセス全体に対して一つしか設定できない。マルチスレッドプログラムでは、カーネルが任意のスレッドにシグナルを配送するため、特定のスレッドに偏る可能性がある。Linuxではtimer_create(2)とCLOCK_THREAD_CPUTIME_IDを使ってスレッドごとのタイマーを設定する方が望ましい。

4.2.2 timer_createによるスレッド単位のサンプリング

#include <time.h>
#include <signal.h>

void setup_thread_timer(pthread_t thread) {
    struct sigevent sev = {
        .sigev_notify = SIGEV_THREAD_ID,
        .sigev_signo = SIGPROF,
        ._sigev_un._tid = pthread_gettid_np(thread),
    };

    timer_t timerid;
    timer_create(CLOCK_THREAD_CPUTIME_ID, &sev, &timerid);

    struct itimerspec its = {
        .it_interval = { 0, 10000000 },  // 10ms
        .it_value = { 0, 10000000 },
    };
    timer_settime(timerid, 0, &its, NULL);
}

4.3 シグナル以外のサンプリング方式

シグナルベースのサンプリングは広く使われているが、唯一の選択肢ではない。async-signal-safetyの制約、セーフポイントバイアス、計装の要否など、それぞれ異なるトレードオフを持つ複数の方式が実用されている。

4.3.1 専用スレッドによるポーリング方式

別スレッドがnanosleep等で周期的にスリープし、起床時に対象スレッドのスタックを取得する方式である。

// 専用サンプリングスレッドの概念コード
void *sampling_thread(void *arg) {
    struct timespec interval = { 0, 10000000 }; // 10ms

    while (profiling_enabled) {
        nanosleep(&interval, NULL);

        for (int i = 0; i < thread_count; i++) {
            // 言語VMのAPIでスタック取得
            // シグナルハンドラではないため、
            // malloc等の制約を受けない
            suspend_thread(threads[i]);
            capture_stack(threads[i], &sample);
            resume_thread(threads[i]);
        }
    }
    return NULL;
}

async-profiler（Java）のwall-clockモードはこの方式を採用し、専用スレッドが各Javaスレッドを巡回してJVM内部APIでスタックを取得する。RubyのVernierも、サンプリングスレッドがGVL（Giant VM Lock）の状態を観察しながら対象スレッドのスタックを取得する。

最大の利点は、シグナルハンドラのasync-signal-safety制約を受けないことである。mallocやmutex操作も自由に使えるため、実装の自由度が高い。一方で、対象スレッドを安全に一時停止する手段が必要であり、言語VMの内部APIへの依存が生じる。

4.3.2 ptraceベースの外部プロセスサンプリング

プロファイラが別プロセスとして動作し、ptrace(2)で対象プロセスを定期的に停止してレジスタとスタックメモリを読み取る方式である。

// ptraceベースサンプリングの概念コード
void sample_external(pid_t target_pid) {
    // 対象プロセスを停止
    ptrace(PTRACE_ATTACH, target_pid, NULL, NULL);
    waitpid(target_pid, NULL, 0);

    // レジスタ状態を取得
    struct user_regs_struct regs;
    ptrace(PTRACE_GETREGS, target_pid, NULL, &regs);

    // スタックメモリをリモートで読み取り
    struct iovec local = { .iov_base = buf, .iov_len = len };
    struct iovec remote = { .iov_base = (void *)regs.rsp,
                            .iov_len = len };
    process_vm_readv(target_pid, &local, 1, &remote, 1, 0);

    // フレームポインタチェーンを辿ってスタックウォーク
    walk_remote_stack(&regs, buf, &sample);

    // 対象プロセスを再開
    ptrace(PTRACE_DETACH, target_pid, NULL, NULL);
}

py-spy（Python）とrbspy（Ruby）がこの方式の代表例である。外部プロセスからprocess_vm_readvでPythonのPyFrameObjectチェーンやRubyのVM制御フレームを直接読み取る。対象プログラムへの変更が一切不要であり、実行中の本番プロセスにもアタッチできる点が最大の利点である。

ただし、ptraceによるプロセス停止はコンテキストスイッチを2回伴うため比較的重く、高頻度サンプリング（1ms以下）には不向きである。また、対象言語ランタイムの内部データ構造（フレームオブジェクトのレイアウトやポインタの辿り方）をプロファイラ側が知っている必要がある。

4.3.3 perf_event_open + mmapリングバッファ方式

カーネルのperf_event_open(2)でPMUイベントやソフトウェアイベントを設定し、カーネルがサンプルをmmapされたリングバッファに直接書き込む方式である。ユーザー空間はリングバッファを読み取るだけでよく、シグナルもptraceも不要である。

// perf_event_open + mmapリングバッファの概念コード
struct perf_event_attr attr = {
    .type = PERF_TYPE_SOFTWARE,
    .config = PERF_COUNT_SW_CPU_CLOCK,
    .sample_period = 10000000, // 10ms相当
    .sample_type = PERF_SAMPLE_IP | PERF_SAMPLE_CALLCHAIN
                   | PERF_SAMPLE_TID,
    .disabled = 1,
};

int fd = perf_event_open(&attr, pid, cpu, -1, 0);

// リングバッファをmmap
void *mmap_buf = mmap(NULL,
    (1 + num_pages) * page_size,
    PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

// カーネルがサンプルを書き込むので、
// ユーザー空間は読み取るだけ
ioctl(fd, PERF_EVENT_IOC_ENABLE, 0);

// 読み取りループ
struct perf_event_mmap_page *header = mmap_buf;
while (profiling) {
    // header->data_headとdata_tailで
    // リングバッファの新しいデータを読み取る
    process_samples(header);
}

perf recordコマンドやAndroidのsimpleperfがこの方式を使用している。カーネル空間でサンプリングとスタックウォーク（PERF_SAMPLE_CALLCHAIN）が完結するため、ユーザー空間への介入が最小限で済む。PMUイベント（キャッシュミス、分岐予測ミス等）をサンプリングのトリガーにできる点も、シグナルベースの方式にはない利点である。

一方で、カーネルが取得できるのはネイティブコードのコールチェーンのみであり、JavaやPython等のマネージドスタックフレームはカーネルからは見えない。CAP_PERFMON権限が必要な場合もある。

4.3.4 セーフポイントポーリング方式

言語ランタイムがセーフポイント（safepoint）と呼ばれる制御点を持ち、各スレッドが周期的にフラグを確認して、自発的にスタックを報告する方式である。

// セーフポイントポーリングの概念
// コンパイラが生成するコードにセーフポイントチェックが挿入される

loop:
    // ... アプリケーションの処理 ...

    // セーフポイントチェック（コンパイラが挿入）
    if (*safepoint_flag) {
        // プロファイラがフラグをセットしていれば
        // ここでスタックを報告
        report_stack_at_safepoint();
    }

    goto loop;

JVMのJFR（Java Flight Recorder）が代表例であり、JVMが各スレッドにセーフポイントを要求し、到達時にスタックを取得する。Goのruntime/pprofも、goroutineスケジューラがスケジューリングポイント（関数呼び出しやチャネル操作等）でスタックを記録する仕組みを持つ。.NETのEventPipeもGCセーフポイントでスタックを取得する。

スタックが常に「安全な状態」で取得されるため、不完全なフレームや壊れたスタックのリスクがない点が最大の利点である。GCとの協調も容易である。

ただし、セーフポイントバイアスが生じうるという問題がある。サンプルがセーフポイントの位置でしか取得されないため、プロファイル結果に偏りが生じる。

このバイアスの影響度は、プロファイリングの粒度とランタイムのセーフポイント挿入戦略に依存する。現代のJVM（JDK 10以降）では、Loop Strip Mining（JEP 401相当）によりループのバックエッジにセーフポイントが挿入される。このため、ループを含むメソッドはセーフポイント到達時にスタック上に存在し、メソッドレベルのプロファイリングでは実質的にバイアスが問題にならない。

一方、行レベルのプロファイリングではバイアスが残る。ループ内のどの行で時間を消費しているかはセーフポイントの位置に引きずられるため、正確な行単位の分布は得られない。また、JDK 10より前のJVMでは、counted loop（カウンタ付きforループ）のバックエッジにもセーフポイントが挿入されず、ループ全体がプロファイルから消えるという深刻な問題があった。

ネイティブコード実行中の扱い: セーフポイント方式ではネイティブコード（C拡張、JNI関数等）の実行中にサンプルが取得されないため、CPU集約的なネイティブ処理が見えないのではないかという懸念がある。しかし、前節で論じた重み付きサンプリングを行っていれば、メソッドレベルではこの問題は自然に解消される。セーフポイントごとにタイムスタンプを記録し、前回セーフポイントからの経過時間を重みとして使えば、ネイティブコード実行で間隔が長くなった分だけ重みが大きくなり、呼び出し元メソッドのコストとして正しく帰属される。ネイティブ/マネージド境界に特別な計装を加える必要はない。

ただし、重み付きサンプリングでもネイティブコードの内部で何が起きているか（どのネイティブ関数が重いか）は見えない。この限界を超えるには、ネイティブコード実行中にもサンプルを取得する方式が必要になる。

セーフポイントバイアスの研究と対策の発展

セーフポイントバイアスの問題を最初に実証的に示したのはMytkowicz et al.の研究（”Evaluating the Accuracy of Java Profilers”, PLDI 2010）であり、当時広く使われていた4つのJavaプロファイラ（xprof、hprof、JProfiler、YourKit）がホットメソッドの特定結果で互いに一致しないことを示した。この研究を契機として、セーフポイントに依存しない以下のような手法が実用化されている。

  • 非同期サンプリング: async-profilerはシグナルベースのAsyncGetCallTraceを採用し、セーフポイントに依存せず任意の実行地点でサンプルを取得する。Honest Profilerも同じAPIを使用する。ネイティブコード実行中のスレッドにもシグナルが配送されるため、行レベルの精度が得られ、ネイティブコード内部の処理も可視化できる
  • CPUタイマーによるサンプリング: JDK 25で導入されたJEP 509（JFR CPU-Time Profiling）は、POSIXのスレッド単位CPUタイマーを使用してネイティブコード実行中にもSIGPROFを発火させる。セーフポイントを経由しないため、暗号ライブラリや圧縮ライブラリ等のCPU集約的なネイティブ処理も正しく計上される
  • 協調的サンプリング: 同じくJDK 25のJEP 518（JFR Cooperative Sampling）は、シグナルハンドラ内でトップフレームのPC/SP/FPを記録し、後続のセーフポイントで完全なスタックを再構成する。シグナル時点の正確なトップフレーム情報とセーフポイントでの安全なスタックウォークを組み合わせることで、バイアスの少ないプロファイルと安全性を両立させる

なお、Burchell et al.（”Don’t Trust Your Profiler”, MPLR 2023）の研究では、async-profiler、Honest Profiler、JFR、JProfiler、perf、YourKitの精度を実証的に比較し、プロファイラ間でホットメソッドの報告が大きく異なりうることを示している。セーフポイント方式に限らず、すべてのサンプリング方式にそれぞれのバイアス源があり、単一のプロファイラの結果を鵜呑みにすべきではないことを示唆する結果である。

4.3.5 eBPFベースのカーネル内サンプリング

eBPFプログラムをperfイベントやタイマーに接続し、カーネル内でスタックトレースの取得と集約まで行う方式である。

// eBPFベースのプロファイラ（概念コード）
// perfイベントに接続されたBPFプログラム
SEC("perf_event")
int do_sample(struct bpf_perf_event_data *ctx) {
    u64 id = bpf_get_current_pid_tgid();
    u32 pid = id >> 32;

    // カーネル内でスタックトレースを取得
    int stack_id = bpf_get_stackid(
        ctx, &stack_map,
        BPF_F_USER_STACK | BPF_F_FAST_STACK_CMP);

    // BPF map内で直接集約（カウント）
    struct stack_count *count =
        bpf_map_lookup_elem(&counts, &stack_id);
    if (count) {
        __sync_fetch_and_add(&count->value, 1);
    }

    return 0;
}

bcc toolsのprofileツール、Parca Agent、Pyroscope（Grafana）などが採用している。ユーザー空間への介入が最小限であり、カーネル内でスタックトレースの集約まで行うためデータ転送量が少ない。

ただし、BPFプログラムの命令数制限やループ制限がスタックウォークの深さを制約する場合がある。また、perf_event_open方式と同様に、ユーザー空間のマネージドスタックはBPFから直接取得できない。

4.4.3 サンプリングバイアスの問題

一定間隔でサンプリングすると、周期的なパターンを持つプログラムでバイアスが生じる可能性がある（ロックステップ問題）。この問題を回避するため、多くのプロファイラはサンプリング間隔にジッター（乱数による揺らぎ）を加える。

    // ±20%のジッター
    long jitter = (random() % (base_interval_ns / 5))
                  - base_interval_ns / 10;
    return base_interval_ns + jitter;
}

4.5 不均一なサンプリング間隔の補正

4.5.1 なぜサンプリング間隔は不均一になるのか

前節で述べたジッターの意図的な導入に加え、実際のシステムではさまざまな要因でサンプリング間隔が不均一になる。

  • シグナル配送の遅延: カーネルの割り込み禁止区間やシグナルマスク中はシグナルが遅延する
  • OSスケジューリング: タイマー精度の限界（timer slack）やCPUの電力管理による遅延
  • 適応的サンプリングレート: 負荷に応じて間隔を動的に変更するプロファイラがある
  • サンプルのドロップ: バッファフルやシグナルの合一（coalescing）によりサンプルが失われる

これらの要因により、「各サンプルが代表する時間」はサンプルごとに異なる。単純にサンプル数をカウントするだけでは、正確なプロファイル結果が得られない。

4.5.2 原理：重み付きサンプリング

不均一間隔に対する基本原理は、各サンプルに重み（weight）を付与し、重み付きで集計することである。

均一間隔の場合、関数 の推定実行時間割合は単純なサンプル比率で求まる。

不均一間隔の場合は、各サンプル の重み を用いて重み付き推定を行う。

ここで は関数 がコールスタック上に存在するサンプルの集合である。

4.5.3 重みの決め方

サンプルの重み の決め方には、主に2つの方式がある。

後方区間方式（backward interval）は、前回サンプルからの経過時間を重みとする。

「前回のサンプル以降、このサンプルが撮られるまでの間ずっとこの状態だった」という仮定に基づく。実装が単純で、多くのプロファイラがこの方式を採用している。

中点方式（midpoint）は、前後のサンプル間の中点で区切った区間の長さを重みとする。

統計学的にはより精度が高いが、最後のサンプルの処理に工夫が必要になる。

Note

異常に長い間隔を上限値でクランプ（clamp）する処理は重要である。サンプルがドロップした場合、次のサンプルの重みが極端に大きくなり、プロファイル結果を歪める。一般的には名目間隔の2〜5倍を上限とする。

4.5.5 実際のツールにおける対応

実際の主要プロファイラでは、以下のように不均一間隔への対応が行われている。

pprof形式では、Sampleメッセージのvalueフィールドに重みを格納できる設計になっている。たとえばCPUプロファイルでは、サンプル数（count）とCPU時間（nanoseconds）を別々のvalue列として保持する。

  repeated uint64 location_id = 1;
  repeated int64 value = 2;  // 例: [count=1, cpu_nanos=10000000]
}

Go runtimeのCPUプロファイラは、各サンプルに実際の経過期間をvalueとして記録する。runtime/pprofパッケージが自動的にこの処理を行うため、ユーザーは意識する必要がない。

Linux perfはPERF_SAMPLE_PERIODフラグにより各サンプルの実際の期間を記録できる。perf reportのデフォルトではサンプル数ベースの表示だが、内部的には期間情報を保持している。

async-profiler（Java）のwall-clockモードでは、スレッドの実際の経過時間を考慮して重み付けを行う。

4.5.6 適応的サンプリングレートでの注意点

負荷に応じてサンプリングレートを動的に変更する適応的サンプリング（adaptive sampling）では、重み付き集計が必須となる。レート変更のタイミングとともに、その時点でのサンプリング間隔をメタデータとして記録することが重要である。

struct rate_change_event {
    uint64_t timestamp_ns;
    uint64_t new_interval_ns;
};

// レート変更時に記録
void change_sampling_rate(uint64_t new_interval_ns) {
    record_rate_change(clock_gettime_ns(CLOCK_MONOTONIC),
                       new_interval_ns);
    update_timer(new_interval_ns);
}

レート変更の記録がなければ、高負荷時（サンプリング頻度が低い期間）と低負荷時（サンプリング頻度が高い期間）の重みを正しく計算できず、低負荷時の処理が過大評価される結果となる。

4.6.3 ucontextからのスタックウォーク

シグナルハンドラの第3引数ucontextには、シグナル受信時のCPUレジスタ状態が保存されている。ここからプログラムカウンタとフレームポインタを取得して、中断されたコンテキストのスタックをウォークできる。

#include <ucontext.h>

void walk_stack_from_ucontext(void *ucontext_ptr,
                               void **buffer, int *depth) {
    ucontext_t *uc = (ucontext_t *)ucontext_ptr;
    *depth = 0;

#if defined(__x86_64__)
    // x86_64: RIPとRBPを取得
    void *ip = (void *)uc->uc_mcontext.gregs[REG_RIP];
    void **fp = (void **)uc->uc_mcontext.gregs[REG_RBP];
#elif defined(__aarch64__)
    // AArch64: PCとFP(x29)を取得
    void *ip = (void *)uc->uc_mcontext.pc;
    void **fp = (void **)uc->uc_mcontext.regs[29];
#endif

    buffer[(*depth)++] = ip;  // 現在の命令ポインタ

    // フレームポインタチェーンを辿る
    while (fp && *depth < MAX_STACK_DEPTH) {
        void *return_addr = fp[1];
        if (!return_addr) break;
        buffer[(*depth)++] = return_addr;
        fp = (void **)fp[0];
    }
}

// Wall-clockサンプリングの設定
void setup_wallclock_timer() {
    struct sigevent sev = {
        .sigev_notify = SIGEV_SIGNAL,
        .sigev_signo = SIGALRM,
    };

    timer_t timerid;
    timer_create(CLOCK_REALTIME, &sev, &timerid);

    struct itimerspec its = {
        .it_interval = { 0, 10000000 },  // 10ms
        .it_value = { 0, 10000000 },

Off-CPU分析は、スレッドがCPUから外れた（スケジュールアウトされた）時間を計測する。eBPFのsched_switchトレースポイントを使って実装される。

int handle_switch(struct trace_event_raw_sched_switch *ctx) {
    u64 ts = bpf_ktime_get_ns();
    u32 prev_pid = ctx->prev_pid;
    u32 next_pid = ctx->next_pid;

    // スケジュールアウトされるスレッドの開始時刻を記録

            record_offcpu_sample(next_pid, delta);

#include <time.h>

// スレッドローカルなコールスタック
__thread struct {
    void *func_addr;
    struct timespec enter_time;
} call_stack[1024];
__thread int stack_depth = 0;

void __cyg_profile_func_enter(void *this_fn, void *call_site) {
    if (stack_depth >= 1024) return;

    call_stack[stack_depth].func_addr = this_fn;
    clock_gettime(CLOCK_MONOTONIC, &call_stack[stack_depth].enter_time);
    stack_depth++;
}

void __cyg_profile_func_exit(void *this_fn, void *call_site) {
    if (stack_depth <= 0) return;
    stack_depth--;

    struct timespec exit_time;
    clock_gettime(CLOCK_MONOTONIC, &exit_time);

    long elapsed_ns =
        (exit_time.tv_sec - call_stack[stack_depth].enter_time.tv_sec)
            * 1000000000L
        + (exit_time.tv_nsec - call_stack[stack_depth].enter_time.tv_nsec);

    // 記録（実際はバッファに書き出す）
    record_timing(this_fn, elapsed_ns);
}

        .ptr = ptr,
        .size = size,

    bytes_until_sample -= size;

8.2 JVMTI（JVM Tool Interface）

JVMTIはJVMが提供する公式のプロファイリング・デバッグAPIである。ネイティブエージェント（共有ライブラリ）としてJVMにロードされ、JVMの内部状態にアクセスできる。

8.2.1 JVMTIエージェントの基本構造

#include <jvmti.h>

static jvmtiEnv *jvmti = NULL;

// エージェントのエントリポイント
JNIEXPORT jint JNICALL
Agent_OnLoad(JavaVM *jvm, char *options, void *reserved) {
    // JVMTI環境の取得
    (*jvm)->GetEnv(jvm, (void **)&jvmti, JVMTI_VERSION_1_2);

    // Capabilitiesの要求
    jvmtiCapabilities caps = {0};
    caps.can_generate_method_entry_events = 1;
    caps.can_generate_method_exit_events = 1;
    caps.can_get_line_numbers = 1;
    (*jvmti)->AddCapabilities(jvmti, &caps);

    // イベントコールバックの設定
    jvmtiEventCallbacks callbacks = {0};
    callbacks.MethodEntry = &on_method_entry;
    callbacks.MethodExit = &on_method_exit;
    (*jvmti)->SetEventCallbacks(jvmti, &callbacks, sizeof(callbacks));

    // イベントの有効化
    (*jvmti)->SetEventNotificationMode(jvmti,
        JVMTI_ENABLE, JVMTI_EVENT_METHOD_ENTRY, NULL);
    (*jvmti)->SetEventNotificationMode(jvmti,
        JVMTI_ENABLE, JVMTI_EVENT_METHOD_EXIT, NULL);

    return 0;
}

8.2.2 JVMTIの問題点：Safepoint Bias

JVMTI のGetStackTraceはセーフポイント（safepoint）でしか実行できない。セーフポイントとは、JVMがすべてのスレッドを安全に停止できるポイントであり、以下の場所に設定される。

  • メソッド呼び出し/リターン
  • ループのバックエッジ
  • JNI呼び出し後のリターン
// セーフポイントバイアスの例
void hotLoop() {
    for (int i = 0; i < 1000000; i++) {
        // ループ内のコード
        // セーフポイントはループのバックエッジにのみ存在
        // ループ内部の特定の行でサンプルされることはない
        compute(data[i]);  // ← この行は正確にプロファイルされない
    }
    // ← セーフポイント：ここでサンプルが偏る
}

Warning

JVMTI のGetStackTraceに基づくプロファイラ（VisualVM、JProfiler旧方式など）は、セーフポイントバイアスにより不正確な結果を返す可能性がある。JIT最適化によりセーフポイントが削除されたループ内部のコードは事実上プロファイルできない。

@jdk.jfr.Category("Application")
class DatabaseQueryEvent extends jdk.jfr.Event {
    @jdk.jfr.Label("SQL")
    String sql;

    @jdk.jfr.Label("Duration")
    @jdk.jfr.Timespan
    long duration;

    @jdk.jfr.Label("Rows Returned")

}

    event.sql = sql;

        event.rowCount = countRows(rs);
    } finally {
        event.duration = event.duration;
        event.commit();
    }
}

9.3 sys.monitoring（Python 3.12+）

Python 3.12で導入されたsys.monitoringは、PEP 669で定義された新しいモニタリングAPIである。従来のsys.setprofile/sys.settraceを置き換え、大幅に低いオーバーヘッドを実現する。

9.3.1 設計思想

sys.monitoringの核心は、「関心のあるイベントだけを監視する」という設計である。従来のAPIはすべての関数呼び出しでコールバックが発生したが、新APIでは必要なイベントタイプのみを有効化できる。

import sys

# モニタリングツールの登録
PROFILER_ID = sys.monitoring.PROFILER_ID

# 関心のあるイベントのみを有効化
sys.monitoring.use_tool_id(PROFILER_ID, "my_profiler")
sys.monitoring.set_events(
    PROFILER_ID,
    sys.monitoring.events.PY_START |
    sys.monitoring.events.PY_RETURN
)

# コールバックの設定
def on_py_start(code, instruction_offset):
    # 関数開始時の処理
    record_entry(code)

def on_py_return(code, instruction_offset, retval):
    # 関数リターン時の処理
    record_exit(code)

sys.monitoring.register_callback(
    PROFILER_ID,
    sys.monitoring.events.PY_START,
    on_py_start
)
sys.monitoring.register_callback(
    PROFILER_ID,
    sys.monitoring.events.PY_RETURN,
    on_py_return
)

gvl_event_callback(rb_event_flag_t event,
                   const rb_internal_thread_event_data_t *data,
                   void *user_data) {

    case RUBY_INTERNAL_THREAD_EVENT_READY:

        break;

        break;

        break;
    }
}

13. フレームグラフと可視化技術

13.1 フレームグラフの原理

フレームグラフ（Flame Graph）は、2011年にBrendan Greggによって考案されたプロファイルデータの可視化手法である。スタックトレースの集合を一枚の図にまとめることで、ボトルネックを直感的に把握できる。

13.1.1 フレームグラフの構造

                    ┌───────────────┐
                    │   func_d (5%) │
          ┌─────────┼───────────────┤
          │func_c   │               │
          │ (15%)   │   func_e(10%) │
┌─────────┼─────────┼───────────────┤
│         │         │               │
│func_a   │  func_b (30%)          │
│ (20%)   │                         │
├─────────┼─────────────────────────┤
│                                   │
│           main (100%)             │
│                                   │
└───────────────────────────────────┘

フレームグラフの各要素の意味は以下の通り。

  • X軸: サンプル数に比例した幅。時間順ではない（アルファベット順にソートされている）
  • Y軸: コールスタックの深さ。下が呼び出し元、上が呼び出し先
  • 各ボックス: 一つの関数。幅がサンプル中での出現割合を表す
  • 色: 通常はランダムまたはパレットに基づく。意味を持たせる場合もある

Important

フレームグラフのX軸は時間を表さない。同じ行のボックスはアルファベット順にソートされているだけである。時間的な順序を表すにはFlamescope（時系列×スタック）を使用する。

14. 継続的プロファイリング

14.1 継続的プロファイリングとは

継続的プロファイリング（Continuous Profiling）は、本番環境で常時プロファイリングを実行し、プロファイルデータを収集・蓄積・分析する手法である。Google社内では2010年頃から「Google-Wide Profiling（GWP）」として運用されてきた。

14.1.1 なぜ継続的プロファイリングが必要か

従来のプロファイリングは開発環境で問題が再現できた場合にのみ行われていたが、以下の理由で本番環境での継続的プロファイリングが重要視されている。

  • 本番環境特有のワークロード: 開発環境では再現できないアクセスパターンやデータ量
  • リグレッション検出: デプロイごとの性能変化を自動検出
  • コスト最適化: CPU使用率の高い関数を特定し、クラウドコストを削減
  • インシデント調査: 問題発生時に過去のプロファイルと比較

14.2 低オーバーヘッドの設計原則

継続的プロファイリングで最も重要な要件は、本番環境に影響を与えないほどの低オーバーヘッドである。

14.3 Google-Wide Profiling（GWP）

GWPはGoogleが社内で運用する継続的プロファイリングシステムである。2010年のACM論文で発表された。

14.3.1 GWPの設計

  1. フリート全体の統計的ビュー: 個々のインスタンスではなく、サービス全体のプロファイルを集約
  2. 低サンプリングレート: 各マシンで1秒間に数回のサンプリング
  3. ランダムサンプリング: マシンごとにサンプリング間隔をランダム化
  4. 集中型ストレージ: すべてのプロファイルをBorgのストレージに保存

14.3.2 GWPの成果

Googleの論文によると、GWPにより以下の成果が報告されている。

  • フリート全体のCPU使用効率を数%改善
  • メモリ使用量の最適化で数ペタバイトの節約
  • デプロイ後の性能回帰を数分以内に検出

15.2.1 シグナルベースのCPUサンプリング

最も基本的なサンプリングプロファイラをCで実装する。

// mini_profiler.c - 最小限のサンプリングプロファイラ
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <sys/time.h>
#include <ucontext.h>
#include <string.h>
#include <execinfo.h>

#define MAX_STACK_DEPTH 64
#define MAX_SAMPLES 100000

// サンプルの構造体
typedef struct {
    void *frames[MAX_STACK_DEPTH];
    int depth;
} sample_t;

// グローバルなサンプルバッファ
static sample_t g_samples[MAX_SAMPLES];
static volatile int g_sample_count = 0;

// SIGPROFハンドラ
static void sigprof_handler(int sig, siginfo_t *info,
                             void *ucontext) {
    if (g_sample_count >= MAX_SAMPLES) return;

    sample_t *s = &g_samples[g_sample_count];

    // ucontextからスタックトレースを取得
    ucontext_t *uc = (ucontext_t *)ucontext;
    s->depth = 0;

    // 現在のIPを記録
#if defined(__x86_64__)
    s->frames[s->depth++] =
        (void *)uc->uc_mcontext.gregs[REG_RIP];
    void **fp = (void **)uc->uc_mcontext.gregs[REG_RBP];
#elif defined(__aarch64__)
    s->frames[s->depth++] = (void *)uc->uc_mcontext.pc;
    void **fp = (void **)uc->uc_mcontext.regs[29];
#endif

    // フレームポインタチェーンを辿る
    while (fp && s->depth < MAX_STACK_DEPTH) {
        void *ret_addr = fp[1];
        if (!ret_addr) break;

        // スタック範囲の妥当性チェック
        if ((uintptr_t)fp < 0x1000) break;
        if ((uintptr_t)fp[0] <= (uintptr_t)fp) break;

        s->frames[s->depth++] = ret_addr;
        fp = (void **)fp[0];
    }

    g_sample_count++;
}

// プロファイラの開始
void profiler_start(int interval_usec) {
    // シグナルハンドラの設定
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_sigaction = sigprof_handler;
    sa.sa_flags = SA_SIGINFO | SA_RESTART;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGPROF, &sa, NULL);

    // タイマーの設定
    struct itimerval timer;
    timer.it_interval.tv_sec = 0;
    timer.it_interval.tv_usec = interval_usec;
    timer.it_value = timer.it_interval;
    setitimer(ITIMER_PROF, &timer, NULL);

    fprintf(stderr, "[profiler] Started (interval=%d us)\n",
            interval_usec);
}

// プロファイラの停止とレポート出力
void profiler_stop(void) {
    // タイマーの停止
    struct itimerval timer;
    memset(&timer, 0, sizeof(timer));
    setitimer(ITIMER_PROF, &timer, NULL);

    fprintf(stderr, "[profiler] Stopped. %d samples collected.\n",
            g_sample_count);

    // 折りたたみ形式で出力
    for (int i = 0; i < g_sample_count; i++) {
        sample_t *s = &g_samples[i];
        // スタックを逆順に出力（ルートから）
        for (int j = s->depth - 1; j >= 0; j--) {
            Dl_info info;
            if (dladdr(s->frames[j], &info) && info.dli_sname) {
                printf("%s", info.dli_sname);
            } else {
                printf("0x%lx", (unsigned long)s->frames[j]);
            }
            if (j > 0) printf(";");
        }
        printf(" 1\n");
    }
}

15.3.1 ELFバイナリからのシンボル取得

// symbol_resolver.c
#include <elf.h>
#include <fcntl.h>
#include <sys/mman.h>
#include <sys/stat.h>

typedef struct {
    const char *name;
    uintptr_t addr;
    size_t size;
} symbol_info_t;

// ELFファイルからシンボルテーブルを読み取る
int load_symbols(const char *path, symbol_info_t **symbols,
                 int *count) {
    int fd = open(path, O_RDONLY);
    struct stat st;
    fstat(fd, &st);

    void *base = mmap(NULL, st.st_size, PROT_READ,
                      MAP_PRIVATE, fd, 0);

    Elf64_Ehdr *ehdr = (Elf64_Ehdr *)base;
    Elf64_Shdr *shdrs = (Elf64_Shdr *)((char *)base
                         + ehdr->e_shoff);

    // .symtabセクションを探す
    for (int i = 0; i < ehdr->e_shnum; i++) {
        if (shdrs[i].sh_type == SHT_SYMTAB) {
            Elf64_Sym *syms = (Elf64_Sym *)((char *)base
                               + shdrs[i].sh_offset);
            int nsyms = shdrs[i].sh_size / sizeof(Elf64_Sym);
            char *strtab = (char *)base
                           + shdrs[shdrs[i].sh_link].sh_offset;

            // 関数シンボルのみを抽出
            *symbols = calloc(nsyms, sizeof(symbol_info_t));
            *count = 0;
            for (int j = 0; j < nsyms; j++) {
                if (ELF64_ST_TYPE(syms[j].st_info) == STT_FUNC
                    && syms[j].st_value != 0) {
                    (*symbols)[*count] = (symbol_info_t){
                        .name = strdup(strtab + syms[j].st_name),
                        .addr = syms[j].st_value,
                        .size = syms[j].st_size,
                    };
                    (*count)++;
                }
            }
            break;
        }
    }

    munmap(base, st.st_size);
    close(fd);
    return 0;
}

// アドレスからシンボルを検索（バイナリサーチ）
const char *resolve_symbol(uintptr_t addr,
                           symbol_info_t *symbols,
                           int count) {
    int lo = 0, hi = count - 1;
    while (lo <= hi) {
        int mid = (lo + hi) / 2;
        if (addr < symbols[mid].addr) {
            hi = mid - 1;
        } else if (addr >= symbols[mid].addr
                   + symbols[mid].size) {
            lo = mid + 1;
        } else {
            return symbols[mid].name;
        }
    }
    return NULL;
}

15.6 Step 5: eBPFベースのプロファイラ

15.6.1 BCC（BPF Compiler Collection）を利用した実装

#!/usr/bin/env python3
# ebpf_profiler.py - eBPFベースのCPUプロファイラ

from bcc import BPF, PerfType, PerfSWConfig
import signal
import sys

# BPFプログラム
bpf_text = """
#include <uapi/linux/ptrace.h>
#include <linux/sched.h>

struct key_t {
    u32 pid;
    int user_stack_id;
    int kernel_stack_id;
    char name[TASK_COMM_LEN];
};

BPF_HASH(counts, struct key_t);
BPF_STACK_TRACE(stack_traces, 16384);

int do_perf_event(struct bpf_perf_event_data *ctx) {
    u32 pid = bpf_get_current_pid_tgid() >> 32;

    // 対象プロセスのフィルタリング
    if (TARGET_PID != 0 && pid != TARGET_PID)
        return 0;

    struct key_t key = {};
    key.pid = pid;
    key.user_stack_id = stack_traces.get_stackid(
        &ctx->regs, BPF_F_USER_STACK);
    key.kernel_stack_id = stack_traces.get_stackid(
        &ctx->regs, 0);
    bpf_get_current_comm(&key.name, sizeof(key.name));

    counts.increment(key);
    return 0;
}
"""

def main():
    target_pid = int(sys.argv[1]) if len(sys.argv) > 1 else 0
    frequency = 99  # Hz

    bpf_text_replaced = bpf_text.replace(
        'TARGET_PID', str(target_pid))
    b = BPF(text=bpf_text_replaced)

    # CPUクロックイベントにアタッチ
    b.attach_perf_event(
        ev_type=PerfType.SOFTWARE,
        ev_config=PerfSWConfig.CPU_CLOCK,
        fn_name="do_perf_event",
        sample_freq=frequency)

    print(f"Profiling{'PID ' + str(target_pid) if target_pid else ' all'}... Ctrl+C to stop.",
          file=sys.stderr)

    def signal_handler(sig, frame):
        print("\n", file=sys.stderr)
        # 結果を折りたたみスタック形式で出力
        counts = b.get_table("counts")
        stack_traces = b.get_table("stack_traces")

        for k, v in sorted(counts.items(),
                            key=lambda x: x[1].value):
            # ユーザースタック
            user_stack = []
            if k.user_stack_id >= 0:
                for addr in stack_traces.walk(k.user_stack_id):
                    sym = b.sym(addr, k.pid, show_module=True)
                    user_stack.append(sym.decode('utf-8', 'replace'))

            # カーネルスタック
            kernel_stack = []
            if k.kernel_stack_id >= 0:
                for addr in stack_traces.walk(k.kernel_stack_id):
                    sym = b.ksym(addr).decode('utf-8', 'replace')
                    kernel_stack.append(sym)

            # 折りたたみ形式で出力
            stack = list(reversed(user_stack)) + \
                    ["--"] + \
                    list(reversed(kernel_stack))
            line = ";".join(stack)
            print(f"{k.name.decode()};{line} {v.value}")

        sys.exit(0)

    signal.signal(signal.SIGINT, signal_handler)
    signal.pause()

if __name__ == "__main__":
    main()

            // ... RETURN命令の実行 ...
            break;

        // ... 他の命令 ...
        }

}
