1. ZendVMとは何か

1.1 PHPの実行モデル

PHPは「共有なし（shared-nothing）」アーキテクチャを採用したスクリプト言語である。Webサーバーが受け取った各リクエストに対して、PHPスクリプトはパース、コンパイル、実行という一連のフェーズを経て処理される。このプロセスの中核を担うのがZend Engine、そしてその仮想マシン部分であるZendVMである。

graph LR A[PHP ソースコード] --> B[Lexer/Tokenizer] B --> C[Parser] C --> D[AST] D --> E[Compiler] E --> F[OPArray] F --> G[ZendVM 実行] G --> H[出力]

PHPの実行モデルにおいて特徴的なのは、各リクエストが独立した実行コンテキストを持つことである。これは言語処理系の設計に大きな影響を与えている。長時間稼働するデーモンプロセスではなく、短命なリクエスト処理を前提として設計されているため、以下のようなトレードオフが生まれる。

  • 起動コストの最小化: コンパイルと実行を高速に行う必要がある
  • メモリ管理の簡素化: リクエスト終了時に一括解放が可能
  • 状態の隔離: グローバル状態の共有を気にする必要がない

Note

PHP 8.1以降のFiber、およびRoadRunner・FrankenPHPのようなアプリケーションサーバーの登場により、長時間稼働するPHPプロセスも一般的になりつつある。しかし、ZendVMの基本設計は依然としてリクエスト単位の実行モデルに基づいている。

1.2 Zend Engineの歴史

Zend Engineの名前は、開発者であるZeev SuraskiとAndi Gutmansの名前に由来する（Zeev + Andi = Zend）。その歴史はPHPの進化と密接に結びついている。

バージョン PHP バージョン 主な変更点
Zend Engine 1.0 PHP 4 (2000) 初版。参照カウントによるメモリ管理
Zend Engine 2.0 PHP 5 (2004) オブジェクトモデルの刷新、例外処理
Zend Engine 3.0 PHP 7 (2015) zvalのリファクタリング、大幅な性能改善
— PHP 8 (2020) JITコンパイラ導入、名前付き引数、Union型

Note

PHP 8のZend Engineには公式なメジャーバージョン番号の付与がなく、PHP公式ドキュメントでも「Zend Engine 4.0」という呼称は使われていない。PHP 8はZend Engine 3の延長線上で、JIT等の大きな機能追加が行われたものである。

特にPHP 7におけるZend Engine 3.0は、言語処理系の設計として非常に興味深い事例である。Dmitry Stogovを中心としたチームが、内部データ構造の根本的なリファクタリングを行い、PHPのメモリ使用量と実行速度を劇的に改善した。この改善は、新しいアルゴリズムの導入ではなく、データ構造のメモリレイアウト最適化という、実装レベルの改善によって達成された点が注目に値する。

1.3 ZendVMの位置づけ

ZendVMは、いわゆるレジスタマシンとスタックマシンのハイブリッドである。形式的にはレジスタベースのVMであるが、オペランドの配置方法にスタック的な要素を持つ。

graph TD subgraph "Zend Engine" A[Scanner/Lexer] --> B[Parser] B --> C[AST Builder] C --> D[Compiler] D --> E[Optimizer] E --> F[VM Executor] end subgraph "Extensions" G[Standard Library] H[OPcache] I[その他の拡張] end F --> G F --> H F --> I

ZendVMの設計上の特徴を整理すると以下のようになる。

1.3.1 レジスタベースのアーキテクチャ

JVMやCPython VMがスタックベースのアーキテクチャを採用しているのに対し、ZendVMはレジスタベース（より正確には、3アドレス形式）を採用している。各命令は最大2つのオペランドと1つの結果格納先を持つ。

ZEND_ADD  op1, op2, result

レジスタベースの利点として、同等の処理をより少ない命令数で表現できることが挙げられる。スタックマシンで a + b を計算するには LOAD a, LOAD b, ADD の3命令が必要だが、レジスタマシンでは ADD a, b, result の1命令で済む。

1.3.2 専用メモリ領域

ZendVMの「レジスタ」は、CPUのレジスタのような固定数のハードウェアレジスタではなく、コンパイル時に割り当てられる一時変数（Temporary Variable）の配列である。この配列は各関数のスタックフレームの一部として確保される。

1.3.3 OPcache統合

ZendVMは、コンパイル結果をキャッシュするOPcacheと密接に統合されている。OPcacheは共有メモリ上にコンパイル済みのオペコード配列を保持し、再コンパイルのオーバーヘッドを排除する。これにより、PHPの「リクエストごとにコンパイル」というモデルのコストを実質的にゼロに近づけている。

2. アーキテクチャ概要

2.1 コンパイルパイプライン

ZendVMの実行パイプラインは、ソースコードから実行結果までの一連の変換プロセスとして理解できる。各フェーズは明確に分離されており、それぞれが独立したデータ構造を入出力とする。

2.1.1 レキシカル解析（Lexer）

zend_language_scanner.l はre2c1を用いて記述されたレキサーである。re2cはlex/flexの代替であり、生成されるコードがDFAベースのスキャナとなるため、高速なトークン化が可能である。

PHPのレキサーの特徴として、コンテキスト依存のスキャンがある。PHPはHTMLの中に埋め込まれる言語であるため、レキサーは INITIAL、ST_IN_SCRIPTING、ST_DOUBLE_QUOTES など複数のスキャン状態を持ち、文脈に応じてトークンの解釈を切り替える。

2.1.2 構文解析（Parser）

PHP 7以降、パーサーは直接OPArrayを生成するのではなく、まずAST（抽象構文木）を構築する。これはPHP 5以前のアーキテクチャからの重要な変更点である。

PHP 5では、パーサーが直接オペコードを生成していた。この方式は一見効率的に見えるが、以下の問題があった。

  • コンパイル時の最適化が困難
  • 複雑な言語機能（yield、finallyなど）の実装が煩雑
  • パーサーとコンパイラの密結合

AST導入により、構文解析とコード生成が明確に分離され、各フェーズを独立して改善できるようになった。

/* PHP 7+ のコンパイルフロー */
void zend_compile(zend_ast *ast) {
    /* ASTノードの種類に応じてオペコードを生成 */
    switch (ast->kind) {
        case ZEND_AST_ASSIGN:
            zend_compile_assign(ast);
            break;
        case ZEND_AST_BINARY_OP:
            zend_compile_binary_op(ast);
            break;
        /* ... */
    }
}

2.1.3 コンパイラ

コンパイラ（zend_compile.c）はASTを走査し、OPArray（オペコード配列）を生成する。コンパイルは関数/メソッド単位で行われ、各関数が一つのOPArrayに対応する。グローバルスコープのコードもまた、一つの「擬似関数」としてコンパイルされる。

コンパイラの主要な責務は以下の通りである。

  1. オペコードの生成: AST ノードを対応するオペコード列に変換
  2. 変数の管理: ローカル変数のCV（Compiled Variable）番号の割り当て
  3. 一時変数の割り当て: 中間結果を格納するテンポラリ変数の番号割り当て
  4. ジャンプ先の解決: 制御フロー（if/else、ループ、try/catch）のジャンプ先設定
  5. リテラルテーブルの構築: 文字列リテラル、数値定数などの格納

2.2.1 オペコードの表現

各オペコード（zend_op）は以下の構造を持つ。

struct _zend_op {
    const void *handler;    /* 命令ハンドラ関数へのポインタ */
    znode_op op1;           /* 第1オペランド */
    znode_op op2;           /* 第2オペランド */
    znode_op result;        /* 結果格納先 */
    uint32_t extended_value;/* 追加情報 */
    uint32_t lineno;        /* ソースコードの行番号 */

    uint8_t op1_type;       /* op1 の型 */
    uint8_t op2_type;       /* op2 の型 */

handler フィールドは、この命令を実行する関数へのポインタを直接保持する。これはVM起動時（またはOPcacheロード時）に解決され、ディスパッチ時のオペコード→ハンドラ変換のコストを排除する。この設計は間接スレッデッドコード（indirect threaded code）として知られ、単純なswitch文によるディスパッチよりも高速である。

2.4 最適化パイプライン

OPcache拡張に含まれるオプティマイザ（zend_optimizer.c）は、コンパイル後のOPArrayに対して複数の最適化パスを適用する。

主要な最適化パスを以下に概説する。

  • ピープホール最適化（Pass 1）: 定数畳み込みなどの単純な最適化
  • ジャンプ最適化（Pass 3）: 連鎖するジャンプ命令の短縮
  • 関数呼び出し最適化（Pass 4）: 関数呼び出しの最適化
  • CFGベース最適化（Pass 5）/ データフロー解析（Pass 6）: 制御フローグラフに基づく最適化
  • SSA・呼び出しグラフ（Pass 7）/ SCCP（Pass 8）: SSA形式での定数伝搬
  • DCE（Pass 14）: 副作用のない不要なコードの除去

Note

これらの最適化パスはOPcache拡張の一部であり、ZendVM本体には含まれない。OPcacheが無効な環境では最適化は行われない。しかし実運用環境ではOPcacheはほぼ必須であり、ZendVMの性能特性を議論する際にはオプティマイザの存在を前提とすることが一般的である。

2.5 実行時キャッシュ

ZendVMは run_time_cache と呼ばれる、関数ごとのキャッシュ領域を持つ。これは名前解決やプロパティアクセスの結果をキャッシュし、繰り返し実行時の性能を向上させるための仕組みである。

/* 実行時キャッシュの使用例: クラスの名前解決 */
zend_class_entry *ce = CACHED_PTR(opline->extended_value);
if (UNEXPECTED(ce == NULL)) {
    ce = zend_fetch_class_by_name(name, ...);
    CACHE_PTR(opline->extended_value, ce);
}

run_time_cache は各プロセスのリクエスト中に構築されるランタイムデータであり、OPcacheの共有メモリ上にある永続的なOPArrayとは異なる。OPcache が共有メモリに保存するのはコンパイル済みのOPArray（オペコード、リテラル等）であり、run_time_cache のようなランタイムポインタはプロセスごとに個別に管理される。

3.1 zval: ZendVMの基本値型

zval（Zend Value）は、ZendVMにおけるすべての値の統一的な表現である。PHPの変数が保持する値は、その型にかかわらず、すべてzvalとして表現される。

3.1.1 PHP 7以降のzval構造

PHP 7で行われたzvalのリファクタリングは、ZendVMの歴史における最も重要な変更の一つである。

Note

3.2 型システム

ZendVMの内部型は以下のように定義される。実装: zend_types.h#L600

#define IS_UNDEF     0   /* 未定義 */
#define IS_NULL      1   /* null */
#define IS_FALSE     2   /* false */
#define IS_TRUE      3   /* true */
#define IS_LONG      4   /* 整数 */
#define IS_DOUBLE    5   /* 浮動小数点数 */

#define IS_ARRAY     7   /* 配列 */

3.2.1 型フラグ

type_flags フィールドは、値の特性を示すビットフラグである。

#define IS_TYPE_REFCOUNTED  (1<<0)  /* 参照カウント対象 */
#define IS_TYPE_COLLECTABLE (1<<1)  /* GCの循環参照検出対象 */

これらのフラグにより、VMは値のコピーや解放の際に型に応じた処理を効率的に分岐できる。

/* 値の解放 - フラグベースの分岐 */
static inline void zval_ptr_dtor(zval *zval_ptr) {
    if (Z_REFCOUNTED_P(zval_ptr)) {
        zend_refcounted *ref = Z_COUNTED_P(zval_ptr);
        if (!GC_DELREF(ref)) {
            /* 参照カウントが0になったら解放 */
            rc_dtor_func(ref);
        } else if (GC_MAY_LEAK(ref)) {
            /* 循環参照の可能性がある場合、GCルートバッファに追加 */
            gc_possible_root(ref);
        }
    }
}

3.3 zend_string: 文字列の内部表現

zend_string はPHP 7で導入された文字列の内部表現であり、ZendVMの至る所で使用される。

struct _zend_string {
    zend_refcounted_h gc;   /* 参照カウント & GC情報 (8バイト) */
    zend_ulong h;           /* ハッシュ値のキャッシュ (8バイト) */
    size_t len;             /* 文字列長 (8バイト) */
    char val[1];            /* 文字列データ（フレキシブル配列メンバ） */
};

この設計のポイントは以下の通りである。

  1. ハッシュ値のキャッシュ: 文字列のハッシュ値を h フィールドにキャッシュする。ハッシュテーブルでの検索時に再計算が不要になる
  2. インライン格納: 文字列データが構造体の末尾に直接格納される（フレキシブル配列メンバ）。メモリ割り当てが1回で済み、キャッシュローカリティも向上する
  3. interned string: コンパイル時に確定する文字列（変数名、関数名など）は「インターン化」され、プロセス全体で共有される。参照カウントの操作すら不要になる
/* interned string の判定 */
#define ZSTR_IS_INTERNED(s) (GC_FLAGS(s) & IS_STR_INTERNED)

/* interned string に対する refcount 操作は no-op */
static inline uint32_t zend_string_addref(zend_string *s) {
    if (!ZSTR_IS_INTERNED(s)) {
        return ++GC_REFCOUNT(s);
    }
    return 1;
}

3.4 HashTable: 配列の内部表現

PHPの配列は、ZendVMでは HashTable（zend_array）として実装される。これはPHPの中で最も頻繁に使用されるデータ構造であり、その設計はZendVMの性能に直結する。

typedef struct _zend_array {
    zend_refcounted_h gc;
    union {
        struct {
            uint8_t flags;
            uint8_t _unused;
            uint8_t nIteratorsCount;
            uint8_t _unused2;

3.4.1 メモリレイアウト

HashTableのメモリレイアウトは、ハッシュインデックスとデータ配列が単一のメモリブロックに配置されるよう最適化されている。

メモリ上の配置:
┌─────────────────────────────┐
│ Hash Index [-8]             │  ← arData - 8
│ Hash Index [-7]             │
│ ...                         │
│ Hash Index [-1]             │
├─────────────────────────────┤
│ Bucket[0] (key, val, h)     │  ← arData (arHash はここを指す)
│ Bucket[1]                   │
│ Bucket[2]                   │
│ ...                         │
│ Bucket[nTableSize-1]        │
└─────────────────────────────┘

ハッシュインデックスはデータ配列の直前に配置される。要素の検索は以下の手順で行われる。

  1. キーのハッシュ値を計算（文字列キーの場合はキャッシュ済み）
  2. hash | nTableMask でインデックステーブルのスロットを決定
  3. スロットからBucket配列のインデックスを取得
  4. キーが一致するまで衝突チェーン（Bucket.val.u2.next）をたどる

3.4.2 パック配列の最適化

整数キーが昇順に並ぶ配列（キーの間にギャップがあってもよい）は、PHP 7から「パック配列（packed hashtable）」として最適化される。パック配列ではハッシュインデックステーブル（arHash）が不要となり、キー n の要素は arData[n] に直接配置される。ただし、Bucket構造体自体は通常の配列と同じものが使われる。

/* パック配列: arHash を使わず直接インデックスアクセス */
if (HT_IS_PACKED(ht)) {
    zval *zv = &ht->arData[idx].val;  /* Bucketのval部分を参照 */
}

これにより、ハッシュ計算と衝突チェーンの探索が不要となり、アクセスが高速になる。また arHash が不要な分、メモリ使用量も削減される。

Note

arPacked は共用体のメンバーとして arData と同じ領域を zval * として参照するための別名であり、Bucket構造体が消えるわけではない。

4. 型システムの詳細

4.1 型ジャグリングと型変換

PHPは動的型付け言語であり、ZendVMは実行時に型変換（type juggling）を頻繁に行う。この型変換のルールと実装は、VMの性能と正確性の両面で重要な意味を持つ。

4.1.1 暗黙の型変換

ZendVMが暗黙に型変換を行うのは、主に以下の場面である。

  1. 算術演算: 整数と浮動小数点の混合演算
  2. 文字列から数値への変換: 算術演算時に文字列が数値的に評価される
  3. 比較演算: 異なる型同士の比較
  4. 論理演算: 真偽値への変換
/* 加算命令のハンドラ（簡略化） */
ZEND_VM_HANDLER(1, ZEND_ADD, CONST|TMPVAR|CV, CONST|TMPVAR|CV)
{
    zval *op1, *op2, *result;
    op1 = GET_OP1_ZVAL_PTR(BP_VAR_R);
    op2 = GET_OP2_ZVAL_PTR(BP_VAR_R);
    result = EX_VAR(opline->result.var);

    if (EXPECTED(Z_TYPE_P(op1) == IS_LONG)) {
        if (EXPECTED(Z_TYPE_P(op2) == IS_LONG)) {
            /* 整数 + 整数: 高速パス */
            fast_long_add_function(result, op1, op2);
        } else if (EXPECTED(Z_TYPE_P(op2) == IS_DOUBLE)) {
            /* 整数 + 浮動小数点: 整数を浮動小数点に変換 */
            ZVAL_DOUBLE(result, ((double)Z_LVAL_P(op1)) + Z_DVAL_P(op2));
        }
    } else if (EXPECTED(Z_TYPE_P(op1) == IS_DOUBLE)) {
        /* ... 浮動小数点の処理 ... */
    } else {
        /* スローパス: 汎用的な型変換 */
        add_function(result, op1, op2);
    }
}

Note

EXPECTED / UNEXPECTED マクロは、GCCの __builtin_expect を用いた分岐予測ヒントである。ZendVMでは整数演算が最も頻繁に発生すると想定し、そのパスを「期待される」パスとしてマークしている。

4.1.2 整数オーバーフロー

ZendVMにおける整数（zend_long）は、64ビットプラットフォームでは64ビット符号付き整数である。整数演算がオーバーフローした場合、結果は自動的に浮動小数点数（double）に昇格される。

static inline void fast_long_add_function(zval *result, zval *op1, zval *op2)
{
#if defined(__GNUC__) && defined(__x86_64__)
    /* GCC組み込み関数によるオーバーフロー検出 */
    zend_long r;
    if (__builtin_saddl_overflow(Z_LVAL_P(op1), Z_LVAL_P(op2), &r)) {
        /* オーバーフロー: double に昇格 */
        ZVAL_DOUBLE(result, (double)Z_LVAL_P(op1) + (double)Z_LVAL_P(op2));
    } else {
        ZVAL_LONG(result, r);
    }
#else
    /* ... フォールバック実装 ... */
#endif
}

この設計は、Pythonの任意精度整数やRubyのFixnum/Bignumの自動変換と対照的である。PHPは精度よりも速度を優先し、ハードウェアの整数演算を直接利用する設計を選択している。

4.2 コピーオンライト（CoW）

ZendVMの値セマンティクスの中核を担うのがコピーオンライト（Copy-on-Write, CoW）機構である。PHPでは配列の代入は値コピーのセマンティクスを持つが、実際のコピーは変更が加えられるまで遅延される。

$a = [1, 2, 3];  // 配列を作成
$b = $a;          // 参照カウントが増加するだけ（コピーなし）
$b[] = 4;         // ここで初めて実際のコピーが発生

4.2.1 CoWの仕組み

CoWの判定と実行は、zvalの操作マクロに組み込まれている。

/* 配列の分離（必要な場合のみコピー） */

    zval *__zv = (zv);                              \
    zend_array *__arr = Z_ARR_P(__zv);              \
    if (UNEXPECTED(GC_REFCOUNT(__arr) > 1)) {       \
        /* 共有されている場合、コピーを作成 */        \
        GC_DELREF(__arr);                            \
        ZVAL_ARR(__zv, zend_array_dup(__arr));       \
    }                                               \
} while (0)

4.2.2 不変配列

OPcache環境下では、コンパイル時に確定する定数配列は「不変（immutable）」としてマークされる。不変配列は参照カウント操作の対象外であり、共有メモリ上に配置される。

#define GC_IMMUTABLE  (1 << 4)

/* 不変配列は refcount 操作をスキップ */
if (!(GC_FLAGS(arr) & GC_IMMUTABLE)) {
    GC_ADDREF(arr);
}

4.3 型強制と厳密型

PHP 7.0で導入されたスカラー型宣言は、declare(strict_types=1) によって厳密モード（strict mode）を選択できる。ZendVMはこの設定に基づいて、関数引数の型検証の振る舞いを変える。

/* 引数の型検証 */
static int zend_verify_arg_type(zend_function *zf, uint32_t arg_num,
                                 zval *arg, zend_class_entry *ce)
{
    zend_arg_info *cur_arg_info = &zf->common.arg_info[arg_num - 1];
    zend_type type = cur_arg_info->type;

    if (ZEND_TYPE_IS_SET(type)) {
        if (UNEXPECTED(!zend_check_type(&type, arg, ce,
                /* is_strict */ EX(func)->common.fn_flags & ZEND_ACC_STRICT_TYPES))) {
            /* 型が一致しない */
            zend_verify_arg_error(zf, cur_arg_info, arg_num, arg);
            return 0;
        }
    }
    return 1;
}

Warning

strict_types の設定は呼び出し側のファイルのdeclareに基づく。つまり、同じ関数でも呼び出し元のファイルによって型強制の振る舞いが変わる。これはZendVMの実装において、コールスタックの情報を参照して動的に決定する必要があることを意味する。

4.6 型付きプロパティの内部実装

PHP 7.4で導入された型付きプロパティは、ZendVMに新たな複雑性を追加した。型付きプロパティは書き込み時に型検証が行われるが、参照経由のアクセスに対しても型安全性を保証する必要がある。

class Foo {
    public int $x = 0;
}

$foo = new Foo();
$ref = &$foo->x;
$ref = "not an int";  // TypeError が発生する

この型安全性を実現するため、参照が型付きプロパティを指す場合、zend_reference 構造体の sources フィールドにプロパティの型情報が記録される。参照経由の書き込み時にこの型情報が参照され、型の整合性が検証される。

/* 参照経由の書き込み時の型検証 */
static void zend_verify_ref_assignable_zval(
    zend_reference *ref, zval *zv, bool strict)
{
    zend_property_info *prop;
    ZEND_REF_FOREACH_TYPE_SOURCES(ref, prop) {
        if (!zend_verify_property_type(prop, zv, strict)) {
            /* TypeError */
        }
    } ZEND_REF_FOREACH_TYPE_SOURCES_END();
}

Caution

型付きプロパティと参照の組み合わせは、ZendVMの実装において最も複雑な部分の一つである。参照が複数の型付きプロパティを同時に指す場合、書き込まれる値はすべてのプロパティの型制約を同時に満たす必要がある。この仕組みは正確だが、性能上のコストを伴う。

6. 実行エンジン

6.1 ディスパッチ方式

VMの実行エンジンにおいて、ディスパッチ方式（命令のフェッチと実行への遷移方法）は性能に直結する最重要設計要素である。ZendVMは複数のディスパッチ方式をサポートしており、ビルド時に選択できる。

6.1.1 CALL方式

最も基本的なディスパッチ方式。各オペコードハンドラが通常のC関数として定義され、ディスパッチループから関数ポインタ経由で呼び出される。

/* CALL方式のディスパッチループ（概念的） */
while (1) {
    int ret = ((opcode_handler_t)opline->handler)(ZEND_OPCODE_HANDLER_ARGS_PASSTHRU);
    if (ret != 0) {
        /* VM終了または例外 */
        break;
    }
    opline = EX(opline);
}

CALL方式は最もポータブルだが、関数呼び出しのオーバーヘッド（引数のプッシュ、リターンアドレスの保存、スタックフレームの構築）が各命令の実行ごとに発生する。

6.1.2 SWITCH方式

巨大なswitch文を使用するディスパッチ方式。

/* SWITCH方式のディスパッチ（概念的） */
while (1) {
    switch (opline->opcode) {
        case ZEND_ADD:
            /* ADD の処理 */
            break;
        case ZEND_SUB:
            /* SUB の処理 */
            break;
        /* ... 約200ケース ... */
    }
    opline++;
}

SWITCH方式は関数呼び出しのオーバーヘッドがないが、分岐予測の精度が低下する。すべてのcase文が同一のswitch（同一の間接ジャンプ）を経由するため、CPUの分岐予測器が十分に機能しない。

6.1.3 GOTO方式（デフォルト）

GCC拡張の「ラベルへのgoto」（computed goto）を使用するディスパッチ方式。ZendVMのデフォルトであり、最も高速な方式である。

/* GOTO方式のディスパッチ（概念的） */
static const void *dispatch_table[] = {
    &&ZEND_ADD_LABEL,
    &&ZEND_SUB_LABEL,
    /* ... */
};

ZEND_ADD_LABEL: {
    /* ADD の処理 */
    opline++;
    goto *dispatch_table[opline->opcode];
}

ZEND_SUB_LABEL: {
    /* SUB の処理 */
    opline++;
    goto *dispatch_table[opline->opcode];
}

GOTO方式の優位性は、各ハンドラの末尾にある goto が独立した間接ジャンプとなることにある。CPUの分岐予測器は各ジャンプポイントに対して独立した予測履歴を持てるため、SWITCH方式よりも予測精度が向上する。

Important

GOTO方式はGCC/Clangの拡張機能（&&label によるラベルアドレスの取得）に依存する。MSVC等のコンパイラではサポートされないため、ZendVMはビルド環境に応じてディスパッチ方式を自動選択する。

6.1.4 ハイブリッド方式

PHP 7.2で導入されたハイブリッド方式は、GOTO方式をさらに発展させたものである。各特殊化ハンドラの末尾に直接次のハンドラへのジャンプが埋め込まれる。

/* ハイブリッド方式: CALL + GOTO のハイブリッド */
HYBRID_CASE(ZEND_ADD_SPEC_CV_CV):
    VM_TRACE(ZEND_ADD_SPEC_CV_CV)
    ZEND_ADD_SPEC_CV_CV_HANDLER(ZEND_OPCODE_HANDLER_ARGS_PASSTHRU);
    HYBRID_BREAK();

/* HYBRID_BREAK の定義 */
#define HYBRID_BREAK() \
    goto *(void**)(OPLINE->handler)

ハイブリッド方式では、opline->handler フィールドにオペコード番号ではなく、GOTO方式のラベルアドレスが直接格納される。これにより、ディスパッチテーブルの参照が不要となり、一回の間接ジャンプで次のハンドラに遷移できる。

6.2 execute_data とグローバルレジスタ

ZendVMの実行において最もアクセス頻度が高い変数は execute_data（現在の実行コンテキスト）と opline（現在実行中の命令）である。これらの変数へのアクセスを高速化するため、GCC/Clangのグローバルレジスタ変数機能が活用される。

/* x86-64環境でのグローバルレジスタ変数宣言 */
#ifdef HAVE_GCC_GLOBAL_REGS
    register zend_execute_data *execute_data __asm__("r14");
    register const zend_op *opline __asm__("r15");
#endif

execute_data と opline がCPUレジスタに固定されることで、以下の効果がある。

  1. メモリアクセスの削減（スタック上の変数参照が不要）
  2. 命令列の短縮（レジスタ間接アドレッシングが直接利用可能）
  3. コンパイラの最適化余地の拡大

Warning

グローバルレジスタ変数を使用すると、レジスタ割り当てに使えるレジスタが減少するため、他のコードの性能に影響する可能性がある。ZendVMでは、この機能はVM実行ループ内部でのみ有効であり、通常のC関数には影響しないよう設計されている。

6.3 VM実行のエントリーポイント

ZendVMの実行は zend_execute 関数から開始される。

ZEND_API void zend_execute(zend_op_array *op_array, zval *return_value)
{
    zend_execute_data *execute_data;

    /* スタックフレームの割り当て */
    execute_data = zend_vm_stack_push_call_frame(
        ZEND_CALL_TOP_CODE | ZEND_CALL_HAS_SYMBOL_TABLE,
        (zend_function *)op_array,
        0, NULL);

    /* execute_data の初期化 */
    EX(prev_execute_data) = EG(current_execute_data);
    EX(return_value) = return_value;
    EX(symbol_table) = zend_rebuild_symbol_table();
    EG(current_execute_data) = execute_data;

6.5 実行時キャッシュ（インラインキャッシュ）

ZendVMは動的言語の宿命的なボトルネック——名前解決——を軽減するため、OPArrayごとにインラインキャッシュを持つ。これは run_time_cache と呼ばれるポインタ配列であり、関数検索・クラス解決・プロパティアクセスなど、実行のたびに繰り返される名前ベースのルックアップ結果をキャッシュする。

6.5.1 キャッシュの構造

run_time_cache はOPArrayごとに割り当てられるフラットな void * 配列である。各オペコードは、コンパイル時に割り当てられた固定オフセット（バイト単位）でこの配列にアクセスする。実装: zend_execute.h#L446（アクセスマクロ）、zend_compile.c#L69（スロット割り当て）

/* コンパイル時: キャッシュスロットの割り当て */
static inline uint32_t zend_alloc_cache_slots(unsigned count) {
    zend_op_array *op_array = CG(active_op_array);
    uint32_t ret = op_array->cache_size;    /* 現在の末尾 */
    op_array->cache_size += count * sizeof(void *);
    return ret;  /* 割り当てたスロットのオフセットを返す */
}

/* 実行時: キャッシュへのアクセス */
#define CACHE_ADDR(num)   ((void **)((char *)EX(run_time_cache) + (num)))
#define CACHED_PTR(num)   (*CACHE_ADDR(num))
#define CACHE_PTR(num, p) (*(CACHE_ADDR(num)) = (void *)(p))

コンパイラは各オペコードが必要とするスロット数を把握しており、opline->extended_value や opline->result.num にオフセットを埋め込む。これにより、実行時にはハッシュテーブル検索ではなく、固定オフセットの配列アクセス（1回のポインタ加算）でキャッシュにアクセスできる。

6.5.2 何をキーに、何をキャッシュするか

インラインキャッシュの核心は「何でバリデーションし、何を保存するか」である。ZendVMでは用途に応じて異なるキャッシュ戦略を使い分ける。

関数呼び出しキャッシュ（モノモーフィック）

INIT_FCALL（コンパイル時に関数名が確定するケース）では、1スロットに関数ポインタをキャッシュする。

/* INIT_FCALL: 1スロット */
/* cache_slot[0]: zend_function * */
fbc = CACHED_PTR(opline->result.num);
if (UNEXPECTED(fbc == NULL)) {
    fbc = zend_fetch_function(fname);  /* グローバル関数テーブルをHashTable検索 */
    CACHE_PTR(opline->result.num, fbc);
}
  • キー: なし（暗黙的にオペコード位置に紐づく関数名）
  • キャッシュ対象: zend_function *（関数ポインタ）
  • バリデーション: なし。同一リクエスト内でユーザー定義関数が再定義されることはないため、一度キャッシュすれば有効

メソッド呼び出しキャッシュ（ポリモーフィック）

INIT_METHOD_CALL では、レシーバのクラスによってメソッドが異なる可能性がある。そのため2スロットを使い、クラスエントリをキーとしてバリデーションする。

/* INIT_METHOD_CALL: 2スロット */
/* cache_slot[0]: zend_function * */
/* cache_slot[1]: zend_class_entry *（バリデーション用） */
fbc = CACHED_PTR(opline->result.num);
if (UNEXPECTED(fbc == NULL) ||
    UNEXPECTED(CACHED_PTR(opline->result.num + sizeof(void*)) != called_scope)) {
    /* キャッシュミス: メソッドテーブルをHashTable検索 */
    fbc = zend_hash_find_ptr(&called_scope->function_table, method_name);
    CACHE_PTR(opline->result.num, fbc);
    CACHE_PTR(opline->result.num + sizeof(void*), called_scope);
}
  • キー: zend_class_entry *（オブジェクトのクラス）
  • キャッシュ対象: zend_function *
  • バリデーション: キャッシュされたクラスエントリと現在のオブジェクトのクラスを比較。不一致ならキャッシュを更新

これは1エントリのみを保持するモノモーフィックキャッシュとして実装されている。同一の呼び出しサイトで異なるクラスのオブジェクトが交互に来る場合（メガモーフィック）、キャッシュミスが毎回発生する。

プロパティアクセスキャッシュ

プロパティアクセス（FETCH_OBJ_R 等）は最も精緻なキャッシュを持ち、3スロットを使用する。

/* プロパティアクセス: 3スロット */

/* cache_slot[1]: プロパティオフセット（uintptr_t） */
/* cache_slot[2]: zend_property_info *（型情報） */

  • キャッシュ対象: プロパティの物理オフセット + プロパティ情報
  • バリデーション: クラスエントリの一致を確認

キャッシュヒット時、プロパティアクセスは「クラスエントリの比較 → オフセット取得 → ポインタ加算」の3ステップで完了する。キャッシュミス時は read_property ハンドラ経由でHashTable検索が走り、桁違いに遅い。

6.5.3 無効化（Invalidation）

インラインキャッシュの設計において最も難しいのは無効化（invalidation）である。ZendVMは、PHPのリクエスト分離モデルを活かした巧みな戦略を採っている。

リクエスト単位の一括無効化

run_time_cache はリクエストの開始時にゼロクリアされる。これが最も重要な無効化メカニズムである。

/* OPcacheがOPArrayを共有メモリに保存する際 */
ZEND_MAP_PTR_NEW(op_array->run_time_cache);
/* → 各プロセスが初回実行時に独自のrun_time_cacheを割り当てる */

OPcacheは共有メモリ上にOPArray（オペコード、リテラル等）を永続化するが、run_time_cache は永続化しない。各プロセスがリクエストごとに新しいキャッシュを割り当て、初回アクセス時にNULLからのコールドスタートとなる。

この設計には重要な帰結がある。

  • クラスの再定義やオートロードによる不整合が原理的に起きない: リクエストごとにキャッシュが白紙に戻るため、前のリクエストの古いポインタが残ることがない
  • 明示的な無効化ロジックが不要: 個別のキャッシュエントリを追跡して無効化する必要がない
  • トレードオフ: リクエストの最初の実行パスは必ずコールドミスとなる

ZEND_MAP_PTR: 共有メモリとプロセスローカルの橋渡し

OPcacheの共有メモリ上のOPArrayが持つ run_time_cache フィールドは、直接ポインタではなく ZEND_MAP_PTR と呼ばれる間接参照の仕組みで管理される。

/* 共有メモリ上のOPArrayのrun_time_cache */
/* → 直接ポインタではなく、プロセスローカルな配列へのオフセット */
ZEND_MAP_PTR_GET(op_array->run_time_cache)
/* → CG(map_ptr_base)[offset] を参照 */

共有メモリ上の構造体には生のポインタを格納できない（プロセスごとにアドレスが異なるため）。ZEND_MAP_PTR はプロセスローカルなポインタ配列のオフセットを格納し、実行時にプロセス固有のポインタに解決する。これにより、不変のOPArrayから可変の run_time_cache への参照が安全に実現される。

リクエスト内でのバリデーション

リクエスト内では、キャッシュの無効化は行わない。代わりに、キャッシュの読み取り時にバリデーションを行う。

  • 関数キャッシュ（INIT_FCALL）: バリデーションなし。同一リクエスト内でグローバル関数が消えることはない
  • メソッド・プロパティキャッシュ: クラスエントリの同一性を比較。異なるクラスのオブジェクトが来た場合はキャッシュを上書き
  • クラスキャッシュ: バリデーションなし。一度ロードされたクラスはリクエスト内で不変

このバリデーション戦略は、PHPの言語仕様に由来する。PHPでは同一リクエスト内でクラスを再定義できないため、「クラスエントリが同じ → メソッドテーブルも同じ → プロパティレイアウトも同じ」が保証される。

6.5.4 高速化の効果

インラインキャッシュの効果は、キャッシュミス時のコスト（HashTable検索）とキャッシュヒット時のコスト（ポインタ比較 + 配列アクセス）の差に由来する。

  • HashTable検索: ハッシュ計算 → バケット探索 → 文字列比較 → ポインタ取得。文字列のハッシュ値がキャッシュ済みでも、数十〜数百ナノ秒のオーダー
  • キャッシュヒット: ポインタ比較1回（メソッド/プロパティの場合）+ ポインタ加算1回。数ナノ秒のオーダー

6.5.5 PICのエントリ数と限界

ZendVMのインラインキャッシュは、プロパティ・メソッドとも1エントリのみを保持するモノモーフィックキャッシュである。V8やHotSpotのような多エントリのポリモーフィックインラインキャッシュ（PIC）やメガモーフィックスタブは実装していない。

これはPHPのワークロード特性に基づく設計判断である。

  • PHPの典型的なコードはモノモーフィック（同一の呼び出しサイトで常に同じクラスが使われる）が多い
  • リクエスト分離モデルのため、長時間稼働するプロセスでのメガモーフィックなサイトの蓄積が起きにくい
  • 複数エントリのPICはキャッシュ探索コストが増え、モノモーフィックなケースで不利になる

ただし、異なるクラスが交互にアクセスするパターン（例：ORMがエンティティオブジェクトの配列を処理する場合）では、毎回キャッシュミスが発生し、HashTable検索にフォールバックする。このようなケースでは、JITのガード付き特殊化のほうが有効に機能する。

7. メモリ管理

7.1 ZendMMアロケータ

ZendVMは独自のメモリアロケータ「ZendMM（Zend Memory Manager）」を使用する。ZendMMは、PHPのリクエスト指向実行モデルに最適化されたメモリ管理システムであり、zend_alloc.c に実装されている。

7.1.1 設計目標

ZendMMの設計目標は以下の通りである。

  1. 高速な割り当てと解放: 小さなオブジェクトの頻繁な割り当て・解放を高速に行う
  2. リクエスト終了時の一括解放: リクエスト終了時にすべてのメモリを一括で解放できる
  3. メモリリーク検出: デバッグビルドでのメモリリーク検出を支援する
  4. メモリ使用量の追跡: memory_get_usage() のための正確な使用量追跡

7.1.2 メモリの分類

ZendMMは割り当てサイズに応じて3つのカテゴリに分類する。

/* ページ内のスロット配置 */
static void zend_mm_init_small_page(zend_mm_heap *heap, zend_mm_page *page,
                                     int bin_num)
{
    int size = bin_data_size[bin_num];   /* サイズクラスのサイズ */
    int count = 4096 / size;            /* ページ内のスロット数 */

    /* フリーリストの構築 */
    zend_mm_free_slot *p = (zend_mm_free_slot *)page;
    zend_mm_free_slot *end = (zend_mm_free_slot *)((char *)page + size * count);
    heap->free_slot[bin_num] = p;

    while (p < end) {
        p->next_free_slot = (zend_mm_free_slot *)((char *)p + size);
        p = p->next_free_slot;
    }
    p->next_free_slot = NULL;
}

7.2 リクエストベースのメモリ管理

ZendMMのメモリは2種類に分けられる。

7.2.1 リクエストメモリ

リクエスト処理中に割り当てられ、リクエスト終了時に自動的に解放されるメモリ。通常のPHPコードで使用されるメモリはこちらである。

/* リクエストメモリの割り当て */
void *emalloc(size_t size);
void *ecalloc(size_t nmemb, size_t size);
void *erealloc(void *ptr, size_t size);
void efree(void *ptr);
char *estrdup(const char *s);

7.2.2 永続メモリ

リクエストをまたいで存続するメモリ。拡張の初期化時や、永続的なデータ構造（永続接続など）に使用される。

/* 永続メモリの割り当て（システムの malloc を使用） */
void *pemalloc(size_t size, int persistent);
void *pecalloc(size_t nmemb, size_t size, int persistent);
void pefree(void *ptr, int persistent);

Caution

リクエストメモリと永続メモリの混在は、メモリ破損やセキュリティ問題の原因となる。リクエストメモリ上のオブジェクトが永続メモリ上のオブジェクトを参照していると、リクエスト終了後にダングリングポインタが発生する。拡張開発では、この区別を常に意識する必要がある。

7.2.3 リクエスト終了時の一括解放

リクエスト終了時、ZendMMは個々の efree を呼び出すのではなく、チャンク単位でメモリを一括解放する。

/* リクエスト終了時のメモリ解放 */
void zend_mm_shutdown(zend_mm_heap *heap, int full_shutdown, int silent)
{
    zend_mm_chunk *p = heap->main_chunk;
    zend_mm_chunk *q;

    /* すべてのチャンクを解放 */
    do {
        q = p->next;
        /* チャンク全体をシステムに返却 */
        zend_mm_chunk_free(heap, p, ZEND_MM_CHUNK_SIZE);
        p = q;
    } while (p != heap->main_chunk);
}

この設計により、たとえPHPコードにメモリリークがあっても、リクエスト終了時にすべてのメモリが解放される。これは共有なしアーキテクチャの大きな利点である。

7.3 ガベージコレクション

ZendVMのメモリ管理は基本的に参照カウントベースだが、参照カウントだけでは循環参照を解放できない。ZendVMは循環参照検出のためのガベージコレクタ（GC）を備えている。

10. JITコンパイラ

10.1 JIT導入の背景

PHP 8.0で導入されたJIT（Just-In-Time）コンパイラは、ZendVMの歴史における最大の変革の一つである。JITはOPcache拡張の一部として実装されている。PHP 8.0〜8.3ではDynASMライブラリを使用してネイティブコードを生成していたが、PHP 8.4では新しいIR（Intermediate Representation）フレームワークに基づくJIT実装に刷新された。

10.1.1 なぜJITが必要だったか

PHP 7のZend Engine 3.0は、データ構造の最適化により劇的な性能改善を達成した。しかし、VMレベルの最適化（特殊化ハンドラ、computed goto等）はほぼ限界に達していた。さらなる高速化には、VMの命令ディスパッチオーバーヘッドそのものを排除する必要があった。

10.1.2 JITの効果はワークロードに依存する

JITの効果は、コードの特性によって大きく異なる。JIT RFCでも「PHPの次のパフォーマンス飛躍にはJITが必要」としつつ、その効果がCPUバウンドな処理に集中することを前提としている。

ケース JITの効果 理由
数値計算（Mandelbrot、暗号等） 非常に大きい（数倍〜） 整数・浮動小数点演算がネイティブ命令に直接変換される
文字列処理ループ 中程度 ループのディスパッチオーバーヘッドの削減
典型的なWebアプリケーション 小さい I/O待ちが支配的、C実装の内部関数呼び出しが多い
フレームワーク（Laravel、Symfony等） 小さい DB・テンプレート・ルーティング等のI/O・内部関数比率が高い

なぜWebアプリケーションでは効果が小さいのか

PHPの典型的なWebアプリケーションの実行時間の内訳を考えると、JITが高速化できる部分が限定的であることがわかる。

典型的なWebリクエストの実行時間内訳（概念的）:
┌──────────────────────────────────────────────────┐
│ データベースI/O                    40-60%         │ ← JIT対象外
│ ネットワーク・ファイルI/O           10-20%         │ ← JIT対象外
│ C実装の内部関数（文字列操作等）     10-20%         │ ← JIT対象外
│ PHPユーザーコード実行              10-30%         │ ← JITが高速化する部分
└──────────────────────────────────────────────────┘

JITはPHPユーザーコードのVM命令ディスパッチを排除してネイティブコードに置き換えるが、データベースクエリやファイル読み書きの待ち時間には影響しない。C言語で実装された内部関数（strlen、array_map、json_encode 等）も、すでにネイティブコードとして実行されているためJITの恩恵を受けない。

結果として、PHPユーザーコードの実行部分が仮に2倍速くなっても、全体のスループットへの寄与は限定的になる。

Important

JITは「常に有効化すべき高速化機構」ではなく、CPUバウンドな処理に対して有効な可能性がある最適化として理解するのが適切である。実アプリケーションへの導入にあたっては、必ず計測に基づいて判断すべきである。JITにはメモリ消費（JITバッファ）やコンパイルコストのオーバーヘッドもあり、効果がないワークロードではむしろ有効化しないほうがよい場合もある。PHP 8.4でデフォルトが disable に変更されたのも、この判断を反映している。

IR Framework（PHP 8.4以降）

PHP 8.4では、DynASMに代わりIR（Intermediate Representation）フレームワークに基づく新しいJIT実装が導入された。IRフレームワークは、プラットフォーム非依存な中間表現を経由して最終的なネイティブコードを生成する2段階の方式を採用している。これにより、x86-64に加えてaarch64（ARM64）などの新しいアーキテクチャへの対応が容易になり、IR上での最適化パスの追加も可能になっている。

Note

PHP 8.4のIR JITはアーキテクチャの刷新であり、長期的には最適化の拡張性が向上するが、旧DynASMベースのtracing JITほど実アプリケーションでの評価が十分に蓄積していない（本書執筆時点）。IR JITの性能特性については、今後のバージョンで変化する可能性がある。

10.3 JITモード

ZendVMのJITには2つの主要なモードがある。

10.3.1 Function JIT

関数全体をコンパイル単位とする。関数が呼び出されると、事前に（またはオンデマンドで）関数全体をネイティブコードにコンパイルする。

利点:

  • 関数内の制御フローを完全に把握した最適化が可能
  • コンパイル単位が明確で予測しやすい

欠点:

  • コールドパス（エラー処理など、稀にしか実行されない部分）もコンパイルする
  • 大きな関数ではコンパイル時間が長い

10.3.2 Tracing JIT

実行時のプロファイリング情報に基づき、ホットパス（頻繁に実行されるコードパス）のみをコンパイルする。

利点:

  • ホットパスのみをコンパイルするため、コンパイルコストが低い
  • 実行時の型情報を活用した高度な特殊化が可能

  • トレースの記録・管理のオーバーヘッド
  • サイドエグジット（トレースから外れる）時の処理が複雑

コードバッファは mmap で確保され、実行可能（PROT_EXEC）にマークされる。セキュリティ上の理由から、コードの書き込みと実行は同時に許可されない（W^X: Write XOR Execute）。

}

static void zend_jit_unprotect(void)
{
    /* コードバッファを読み取り+書き込みに変更 */
    mprotect(dasm_buf, dasm_size, PROT_READ | PROT_WRITE);
}

JITネイティブコード 共有メモリ（JITバッファ） 永続（全リクエスト） 不変（生成後は変更しない）
JITメタデータ（jit_extension） 共有メモリ 永続（全リクエスト） 不変
run_time_cache（インラインキャッシュ） プロセスローカルメモリ リクエスト単位 可変
クラスリンク結果 プロセスローカル（継承キャッシュで一部共有） リクエスト単位 可変

この分類が重要なのは、共有メモリに載せられるのは不変データだけという原則があるためである。

  • OPArrayとJITコード: 生成後は変更されない。だから共有メモリに安全に配置できる
  • run_time_cache: 実行時に更新される（キャッシュミス時にポインタを書き込む）。プロセスごとに異なるポインタ値を持つ。だから ZEND_MAP_PTR を介してプロセスローカルに配置する
  • JIT型ガードによるフォールバック: JITコードは型推論に基づいて特殊化されているが、型が変わった場合はサイドエグジットでVMインタプリタにフォールバックする。このフォールバック先はOPArray（共有メモリ）上のオペコードであり、こちらも不変

この設計により、JITコンパイルのコストが最初の1回のみで済み、以降のリクエストでは純粋にネイティブコードの実行性能を享受できる。これはPHPのリクエスト分離モデルとOPcacheの共有メモリアーキテクチャが組み合わさった結果であり、長時間稼働するJVMやV8のJITとは根本的に異なるライフサイクルを持つ。

Note

JITコードが共有メモリ上で不変であることは、deoptimization（最適化の取り消し）の仕組みにも影響する。V8やHotSpotは最適化仮定が崩れたときにJITコードを無効化・再コンパイルするが、ZendVMのJITは共有メモリ上のコードを書き換えない。代わりに、型ガードの失敗時にVMインタプリタにフォールバックし、そのまま実行を続ける。再コンパイルが必要な場合は、次のリクエスト以降に新たなプロファイリング情報に基づいて行われる。

11.1 コンパイラレベルの最適化

ZendVMのコンパイラ（zend_compile.c）は、AST からOPArrayを生成する際にいくつかの基本的な最適化を行う。

11.1.1 定数式の畳み込み

SSA（静的単一代入）形式への変換

SSA形式では、各変数は一度だけ代入される。複数の定義がある場合はφ関数で結合する。

// 元のコード
$x = 0;
for ($i = 0; $i < 100; $i++) {
    $x = $x + $i;
}

// SSA形式
BB0:
  $x_0 = 0
  $i_0 = 0

BB1:
  $x_1 = φ($x_0, $x_2)    // BB0からは$x_0、BB2からは$x_2
  $i_1 = φ($i_0, $i_2)
  if ($i_1 < 100) goto BB2 else goto BB3

BB2:
  $x_2 = $x_1 + $i_1
  $i_2 = $i_1 + 1
  goto BB1

BB3:
  return $x_1

型推論

SSA形式のOPArrayに対して、各変数の取りうる型を推定する。

/* 型推論の結果（ビットマスク） */
typedef uint32_t zend_ssa_var_info;

/* 推論例 */
$x_0: MAY_BE_LONG                    // int(0) なので確実に LONG
$i_0: MAY_BE_LONG                    // int(0) なので確実に LONG
$x_1: MAY_BE_LONG                    // φ関数の引数がすべて LONG
$i_1: MAY_BE_LONG                    // φ関数の引数がすべて LONG
$x_2: MAY_BE_LONG | MAY_BE_DOUBLE    // 加算はオーバーフローの可能性
$i_2: MAY_BE_LONG | MAY_BE_DOUBLE    // 同上

11.2.3 SCCP（Sparse Conditional Constant Propagation）

SCCPは、条件分岐を考慮した定数伝搬を行う（Pass 8）。

// SCCP適用前
function foo($flag) {
    if ($flag) {
        $x = 10;
    } else {
        $x = 10;  // 同じ値
    }
    return $x + 5;
}

// SCCP適用後
function foo($flag) {
    if ($flag) {
        $x = 10;
    } else {
        $x = 10;
    }
    return 15;  // $x + 5 が定数15に畳み込まれる
}

11.2.4 DCE（Dead Code Elimination）

副作用のないコードで、結果が使用されないものを除去する（Pass 14）。

// DCE適用前
$unused = $a + $b;  // $unused は以降使われない
return $c;

// DCE適用後
// $unused の計算は除去される
return $c;

11.3 特殊化ハンドラの割り当て

ZendVMでは、各オペコードに対してオペランドの種別（op1_type, op2_type）に基づく特殊化ハンドラが自動生成される。これはコンパイル時のオペランド種別（CONST, TMP, VAR, CV, UNUSED）に基づくものであり、実行時の値の型（LONG, DOUBLEなど）に基づく特殊化ではない。

/* オペランド種別に基づくハンドラの特殊化（概念的） */
// ZEND_ADD の場合、以下のような特殊化ハンドラが生成される:
// ZEND_ADD_SPEC_CONST_CONST_HANDLER  - 両オペランドが定数
// ZEND_ADD_SPEC_CV_CV_HANDLER        - 両オペランドがCV（ローカル変数）
// ZEND_ADD_SPEC_CV_CONST_HANDLER     - op1がCV、op2が定数
// ZEND_ADD_SPEC_TMPVAR_CV_HANDLER    - op1がTMP/VAR、op2がCV
// ... 他の組み合わせ

各特殊化ハンドラは、オペランドの取得方法が確定しているため、汎用ハンドラよりも効率的である。

/* CV+CV 専用の ADD ハンドラ（概念的） */
static int ZEND_ADD_SPEC_CV_CV_HANDLER(ZEND_OPCODE_HANDLER_ARGS)
{
    zval *op1 = EX_VAR(opline->op1.var);  /* CVとして直接アクセス */
    zval *op2 = EX_VAR(opline->op2.var);  /* CVとして直接アクセス */
    zval *result = EX_VAR(opline->result.var);

    /* 値の型に応じた処理は実行時に判定 */
    add_function(result, op1, op2);

    ZEND_VM_NEXT_OPCODE();
}

Note

SSA型推論の結果（値がLONG, DOUBLEなど）は、JITコンパイラがネイティブコード生成時に活用する。JITでは型推論に基づき、整数専用・浮動小数点専用のネイティブコードを生成し、型ガードで安全性を保証する（JIT章参照）。一方、VMインタプリタのハンドラ特殊化はオペランド種別ベースであり、この2つの仕組みは区別して理解する必要がある。

11.4 定数宣言の収集と置換

OPcacheのPass 15は、定数宣言の収集と置換を行う。これはunsafeな最適化としてデフォルトでは無効になっている。

/* Pass 15: 定数宣言の収集と置換の例 */
define('TAX_RATE', 0.1);

// Pass 15 が有効な場合、TAX_RATE をリテラル 0.1 に置換
$total = $price * TAX_RATE;
// → $total = $price * 0.1;  に最適化される

この最適化では、define() で定義された定数を使用箇所でリテラルに置換する。ただし、実行時に定数定義が条件分岐等で変わる可能性があるケースではプログラムの動作が変わりうるため、デフォルトでは無効とされている。

Caution

Pass 15はunsafe（安全でない）最適化に分類される。有効にする場合は、定数の再定義やオートローダによる副作用がないことを確認する必要がある。また、Pass 16（自明な関数のインライン展開）は関数呼び出し最適化の一部として動作し、小さな関数を呼び出し元に展開する。

12.7 内部関数のフック

zend_execute_internal フックを差し替えることで、すべての内部関数呼び出しをインターセプトできる。

/* 内部関数フックの例 */
static void (*original_execute_internal)(zend_execute_data *, zval *);

static void custom_execute_internal(zend_execute_data *execute_data,
                                     zval *return_value)
{
    /* 前処理: タイミング計測開始 */
    struct timespec start;
    clock_gettime(CLOCK_MONOTONIC, &start);

    /* 元の関数を呼び出し */
    original_execute_internal(execute_data, return_value);

    /* 後処理: 実行時間の記録 */
    struct timespec end;
    clock_gettime(CLOCK_MONOTONIC, &end);
    /* ... */
}

/* フックの設定（拡張のMINIT内） */

zend_execute_internal = custom_execute_internal;

Warning

zend_execute_internal フックはすべての内部関数呼び出しに影響するため、プロファイラ以外の用途で使用する場合は性能への影響を十分に考慮する必要がある。また、JIT有効時にはフックが機能しない場合がある。

}

}

13.1 比較の観点

言語VMの設計は、対象言語のセマンティクス、想定される利用パターン、歴史的な経緯によって大きく異なる。本章では、ZendVMを以下のVMと比較し、設計判断の背景と結果を考察する。

13.9 総合的な考察

13.9.1 ZendVMの設計上の強み

  1. リクエスト指向の最適化: リクエスト分離モデルが、VM内部の複数の設計判断を劇的に簡素化している。
    • メモリ管理: リクエスト終了時にアリーナを一括解放できるため、JVMのZGCやV8のScavengerのような複雑なGCアルゴリズムが不要。参照カウントの弱点である循環参照も、最悪でもリクエスト終了で回収される
    • インラインキャッシュの無効化: run_time_cache をリクエスト開始時にゼロクリアするだけで全キャッシュが無効化される。JVMやV8が必要とする個別エントリの無効化やdeoptimizationの仕組みが不要
    • 並行制御の排除: リクエスト間で状態を共有しないため、実行エンジン内部にロックや同期プリミティブが不要。これはCPUキャッシュの効率にも寄与する
    • OPcacheとの相性: コンパイル結果（不変、共有メモリ）と実行時状態（可変、プロセスローカル）を ZEND_MAP_PTR で明確に分離でき、共有メモリ設計が単純になる
  2. OPcache統合: コンパイル結果の永続キャッシュにより、起動コストを実質ゼロに
  3. 特殊化ハンドラの自動生成: PHPによるメタプログラミングで保守性を確保しつつ性能を最適化
  4. 実用的なパフォーマンス: Webアプリケーションのワークロードに特化した設計判断

13.9.2 ZendVMの設計上の課題

  1. 命令サイズの大きさ: 32バイト/命令はキャッシュ効率に不利
  2. JITの効果の限定性: I/Oバウンドなワークロードではインタプリタとの差が小さい
  3. 長寿命プロセスへの適応: Fiberやasync処理の増加に対するGCの改善余地
  4. 型情報の活用: 静的型情報（型宣言）のVM/JITレベルでの活用はまだ発展途上

13.9.3 言語VM設計への示唆

ZendVMの歴史から得られる重要な示唆は、データ構造の最適化がアルゴリズムの改善に匹敵する性能効果を持つということである。PHP 7のzvalリファクタリングは、新しいアルゴリズムを導入することなく、データレイアウトの改善だけで2倍以上の高速化を達成した。

また、実行モデルとVM設計の整合性が重要であることも示している。ZendVMのリクエスト分離、参照カウント、一括解放という設計は、PHPのWebサーバースクリプトとしての用途に完璧に適合している。逆に、長時間稼働するデーモンプロセスにPHPを使う場合、これらの設計がオーバーヘッドとなる可能性がある。

Tip
